## 1. 结论（先看这一段）

**当前版本不能直接交付到实际生产环境；它可以作为受控试点（pilot）继续验证。**

已经做到的部分是真实的：HEAD 是一个可追踪的可靠性修复冻结提交；在本机与 VPS 干净源码上，
Node 回归、Go 可移植包、Linux amd64 `-race`、`release-check --profile engineering` 都通过；
公网试部署今天完成了一次**真实图片题 → PoW → `/api/redeem` → 业务后端 `/siteverify` → 留言写入 →
同 token 重放被拒**的完整闭环。

但它还不是“生产可交付版本”，原因不是某一个测试没跑，而是下面这些**同时成立**：

1. **正式支持范围没有完成验收**：正式范围是 Linux arm64；本轮只在 x86_64 测试 VPS 上取得了
   amd64 运行证据。`release-check --profile full` 仍是 **INCOMPLETE/3**（上一轮同一 HEAD 的干净
   worktree 结果），`stage4b`、`stage5a`、`stage5b`、`admin-ui`、真实 Firefox、arm64 race/full
   没有在本轮通过。amd64 的 engineering PASS **不能**替代 arm64 full PASS。
2. **`text-image-v1` 仍是 `experimental:true` / `production_ready:false`**。历史 OCR 低/中/高档
   96%/31%/3% 是单一工具、固定配置的严格整串通过率，不是当前 M4，也不是抗现代 AI 的认证；
   人工可读性、辅助技术、真机移动端仍未执行。低档 96% 意味着生产默认**不得**落在低档。
3. **第三层风险打分、题型权重与多生成器选择、统计与分级淘汰、非视觉等价通道、完整管理台
   （题池/审计/凭据轮换页面）没有实现。** 当前是“PoW + 一次性题池 + 站点接入”的工程骨架，
   不是 DESIGN 原始需求完整交付的产品。
4. **持久化有一个项目自己承认的上线阻断**：`internal/store/store.go:83` 固定
   `synchronous=NORMAL`；`docs/DECISIONS.md` 明确写着掉电保证缺口保持上线阻断（B-03）。
   进程崩溃/正常重启有 WAL 保护，但掉电时最近事务可能丢失；对防重放账本而言，丢失方向可能是
   “已消费 token 又能被接受”。
5. **停用/撤销与在途消费的原子性没有闭合**（F-01）：`/siteverify` 的站点检查与
   `ConsumeResponse` 是两个事务；一个已经在途的请求可能在停用提交之后仍然消费成功。
   当前代码与测试的表述比实现更强，必须二选一：收紧实现，或明确放宽语义并改测试/文档。
6. **没有项目自己的公网域名/TLS/DNS/防火墙**。当前 HTTPS 是 instabox 平台入口，不是项目证书、
   域名与反代验收；管理台也没有发布或做浏览器验收。
7. **当前工作树不干净，且没有正式候选 OID/manifest。** 本轮构建收据只证明“这份字节与这份清单
   对得上”，不是可重复构建证明，也没有签名；不能把试部署镜像当成正式发布候选。
8. **容量边界没有达到“300 并发全部成功”**：上一轮在同一 HEAD/实例上的试部署实测约 1.5–2 RPS
   持续通过；瞬时 300 并发时算术题池约 51–92 成功、图片题池约 22–24 成功，其余返回明确的
   `503 challenge-unavailable`。本轮没有重跑压测；这是上一轮的实测事实，不是今天的复跑。
   这是 fail-closed 的容量信号，不是“容量达标”。

因此，本报告的判断是：

> **当前版本是“可在测试 VPS 上真实试部署、可完成业务闭环、工程门禁基本健康”的试点版本；
> 不是“可以直接交付生产”的正式版本。整体测试链路仍差最后一段：你本人的外网实测；
> 以及正式 arm64/full 门禁、F-01/B-03 决策、人工与效果验收、生产 TLS/备份/监控。**

如果“生产”只指低风险表单的 PoW-only 试点，并且明确接受上述边界，可以先小范围使用；
如果“生产”指原设计的生产级人机验证服务，**现在不能上线**。

## 5. 发布阻断项（Release blockers）

### B-01 · P1 · 正式支持范围（Linux arm64）没有完成验收

**事实**：正式范围是 B 路径 / Linux arm64 / UID:GID 1000:1000。本轮在 x86_64 VPS 上完成了
Linux amd64 的 race、engineering、公网闭环；arm64 只做了交叉编译（22/22 测试二进制、
server/ops 静态构建），没有在 arm64 上运行。上一轮同一 HEAD 的干净 worktree `full` 是
`INCOMPLETE/3`；`stage4b/5a/5b/admin-ui` 仍是 BLOCKED/NOT_RUN。

**影响**：不能把 amd64 的 race/engineering 结果写成 arm64 正式验收；也不能把试部署写成正式候选。

**闭合条件**：在隔离的 Linux arm64、UID:GID `1000:1000`、Go 1.27.3、Node 24、Docker、Firefox、
`make`/GCC 可用的环境里，从干净 OID 执行：

```bash
git status --porcelain                 # 必须为空
GOTOOLCHAIN=local go mod verify
GOTOOLCHAIN=local go test -race -count=1 ./...
node docs/scripts/release-check.mjs --profile full
# 必须得到 RESULT=PASS SCRIPT_RC=0；不能用 make 的 0/2 代替
```

任何 BLOCKED/NOT_RUN 都必须保留；不能把 `INCOMPLETE` 写成通过。

### B-02 · P1 · 还没有项目自己的公网入口验收

**事实**：当前公开入口是 instabox 平台 HTTPS 转发到测试夹具；没有项目域名、证书、DNS、
防火墙与 Nginx/Caddy 配置验收。管理台不发布是正确的，但也没有做反代/TLS 验收。

**影响**：可以把测试页给你点，但不能把它当成“生产入口已验收”。

**闭合条件**：确定域名/TLS 来源、反代拓扑、回源地址、真实连接来源与 trust-proxy 网段；
按 `docs/DEPLOYMENT.md` §6/§11 做 `nginx -t`、80/443 日志载体、来源限制与 `/readyz` 验收。

### B-03 · P1 · `synchronous=NORMAL` 的掉电持久化缺口仍是上线阻断

**事实**：`internal/store/store.go:83` 固定 `_pragma=synchronous(NORMAL)`；
`docs/DECISIONS.md` 明确保留该缺口为上线阻断。进程崩溃/正常重启有 WAL 保护，但掉电/OS 崩溃时
最近事务可能丢失。

**影响**：丢失的可能是已提交的 response 消费、撤销或审计记录；方向可能是“已消费 token 又能被接受”。

**建议**：不要静默改成 `FULL`。先做明确决策：

1. 生产前改 `FULL`，在目标 1 vCPU/1GB 上测量写入时延与吞吐影响；或
2. 明确接受 `NORMAL` 的掉电窗口，写进 ADR/运维合同，并在试部署中标注“不是生产持久化认证”。

无论选哪条，都不能把“进程重启后不可重放”写成“掉电后也不可重放”。

### B-04 · P1 · 人工与效果验收仍未完成

- `text-image-v1` 仍是 `experimental:true` / `production_ready:false`；
- 历史 OCR 低/中/高档 96%/31%/3% 是单一工具、固定配置的严格整串通过率，不是当前 M4；
- 人工可读性、辅助技术、真机移动端、题型人工各过 5 次均未执行；
- 管理台的 403/5xx 文案、剪贴板、真机移动端、辅助技术仍是 NOT_RUN；
- 本轮的“人工读图 + 程序化 PoW”是一次功能闭环，不是效果认证。

这些不是工程测试能替代的；试部署可以让你实际点一遍，但仍需单独记录人工证据，
不能自动改 `production_ready`。

### B-05 · P1 · 容量边界不满足“300 并发全部成功”

**事实**：上一轮在同一 HEAD/实例上的试部署实测约 1.5–2 RPS 持续通过；瞬时 300 并发时，
算术题池约 51–92/300 成功（不同池状态），图片题池约 22–24/300 成功，其余是明确的
`503 challenge-unavailable`。本轮没有重跑压测，这是上一轮的实测事实。
生产默认限流是全局 IP 60 RPM、站点 300 RPM；测试时曾临时提高限流，测完已恢复。

**影响**：如果产品要求 300 并发全部成功，当前 pool low/high、图片预算、worker 数量与限流
不满足。503 是 fail-closed 容量信号，但“能正确拒绝”不等于“容量达标”。

**闭合条件**：先定产品目标（持续 RPS / 瞬时并发 / 可接受的 503 比例），再调 pool 水位、
图片桶预算、worker 批量与限流，并在目标硬件上重新验收。不要把测试专用高限流写进生产配置。

### B-06 · P1 · 工作树不干净，没有正式候选 OID/manifest

**事实**：`docs/scripts/stage3b.sh` 有一个未提交的测试断言补丁（接受“不代表/未完成/未经”
三种否定表述，仍要求 `experimental=true`、`production_ready=false`、note 提到 OCR）。
运行时代码未变；上一轮 VPS 上用它跑过 stage3b。当前试部署镜像是本地 `epocha:trial-amd64`，
不是 registry digest；构建收据没有签名。

**影响**：正式候选必须绑定干净 OID、工具链、构建命令、两份二进制 SHA-256 和完整验收结果。
本轮无法把“试部署镜像”当作正式候选。

**建议**：决定保留还是丢弃该测试补丁；提交成干净 OID；重新生成构建收据/manifest；
在 arm64 上跑 full；不要移动/删除历史标签。

## 6. 代码与运维发现

### F-01 · P1 · 停用/撤销与消费的原子性只覆盖 response，不覆盖站点状态

**证据**：

- `internal/api/handlers.go:598` 在 handler 里检查 `!site.Enabled || site.Version != claims.Svid`；
- `internal/api/handlers.go:606` 随后才调用 `ConsumeResponse`；
- `internal/store/store.go:515-525` 的 `ConsumeResponse` 事务只检查 `responses.used=0` /
  `expires_at>now`，**不检查站点 enabled/version，也不检查 secret 是否已被撤销**；
- 现有并发测试只断言“最多成功 1 次”，并允许 0 或 1；没有断言“停用先提交 ⇒ 消费必失败”。

**影响**：一个 `/siteverify` 请求如果在停用提交之前读到 `site.Enabled=true`，在停用提交之后
才执行消费，仍可能成功。`/api/redeem` 的站点状态检查也在 `RedeemAttempt` 事务之外。
窗口很窄，但停用通常正是为了立刻止血，语义不能靠“通常很快”保证。

**建议（二选一，不要含糊）**：

1. **收紧实现**：把 `sites.enabled` 与 `sites.version` 纳入 `ConsumeResponse` 的同一事务
   （在 UPDATE 里加 `EXISTS (SELECT 1 FROM sites ... enabled=1 AND version=?)`），
   并在 `RedeemAttempt` 里对 `site_id` 做同样校验；补确定性交错测试：
   先读站点 → 停用提交 → 再消费，必须失败。
2. **明确放宽语义**：在 DESIGN/ADR 里把“立即失效”改为“停用与在途消费按提交顺序竞争，
   在途请求可成功一次”，并让测试真正覆盖该方向。

当前代码和测试的表述比实现更强，不能同时保留两种说法。

### F-02 · P2 · `MaxSites` 的硬上限在事务外计数

**证据**：`internal/store/sites.go:200` 在 `BeginTx`（约 221 行）之前 `SELECT count(*) FROM sites`；
真正的 `INSERT INTO sites` 在事务内。两个并发管理请求可以都读到 511，然后先后提交，超过 512。

**影响**：`MaxSites` 是 `FindSiteBySecret` 全表扫描上界的一部分；突破上限会让“有界扫描”
这一资源不变量失效。管理面是可信面，风险低于公开面，但仍是可修复的竞态。

**建议**：把计数与插入合并为一条条件 INSERT，或在一个先取得写锁的事务里完成；
补两个独立 DB 句柄并发建站的测试，断言最终行数不超过 512。不要在 `*sql.Tx` 上再执行
`BEGIN IMMEDIATE`（红线 3）。

### F-03 · P2 · 备份“已发布但持久化未确认”仍以退出码 0 结束

**证据**：`internal/store/deploy.go:354-367` 的 `publishBackup` 在数据库与 manifest 都已发布、
但 `syncDirectory` 失败时返回的是 warning，不是错误；`cmd/ops/main.go` 只打印警告并返回 nil。

**影响**：cron/自动化只看退出码时，会把“目录同步失败、持久化尚未确认”当成成功备份。

**建议**：为“已发布但持久化未确认”定义独立退出码或 `--strict` 行为；在自动化配方里把警告
升级为失败；保留“已发布文件不删除”的安全方向。把“备份已发布”和“备份已持久化确认”分开写进
`docs/BACKUP-RESTORE.md`。

### F-04 · P2 · 忽略目录会污染 Go 包清单与发布门禁

**证据**：当前工作树跑 `full` 时，`go-package-inventory` 会把 `release-artifacts/`、`tmp/`
里的历史 `.go` 文件扫进 `./...`；干净 worktree 没有这个 FAIL。

**影响**：同一份源码在不同工作树会得到不同的门禁结果；开发者会误以为是代码问题。

**建议**：正式验收固定使用干净 worktree/隔离源码快照；本机工作树不作为候选。
如要长期改善，可把历史 `.go` 证据移出仓库目录，或在门禁中明确以 Git 清单为准；
不要为了让 `./...` 通过而删除用户的历史证据文件。

### F-05 · P3 · 所有管理凭据都被撤销时，启动日志没有“无可用凭据”的告警

**证据**：`cmd/server/main.go:306` 只在 `len(keys)==0` 时打印“库中没有可用管理凭据”；
`ListAdminKeys` 返回全部行（包括已撤销行）。最后一把凭据被撤销时，`len(keys)>0`，
启动不会告警，但管理 API 实际全部 401。

**影响**：运维在锁死时缺少最直接的启动提示；安全性不受影响，但可运维性变差。

**建议**：统计“当前仍有效”的 admin key 数量，为零时告警；不要自动 bootstrap 或复活旧凭据。

### F-06 · P3 · 20MB 历史评测归档仍被 Git 跟踪

**事实**：`epocha-offline-assets.tar.gz` 为 20,156 KiB，`git ls-files` 可见；README 说明它是
历史开发评测归档，运行时没有自动装载入口，`.dockerignore` 已排除。

**影响**：克隆体积增大；归档里的 `eval-out` 可能包含历史图片与预测，容易让人误以为它是
当前评测基线。它不是秘密材料，也不应在本轮删除（未授权删除既有文件）。

**建议**：下一个干净里程碑决定是否改用 Git LFS/发布附件；在此之前继续明确“不是候选输入”。

### F-07 · P3 · 管理监听器非 loopback 时只告警，不拒绝启动

**证据**：`cmd/server/main.go:310` 对非 loopback 管理地址只打印“请在反代/防火墙侧再加一层
来源限制”，随后继续启动。compose 把管理监听钉在 `127.0.0.1:8081` 且不发布，但直接运行二进制
或用其他编排方式时，`--admin-listen 0.0.0.0:8081` 可以把明文 HTTP 的 Bearer 管理面放到网络上。

**影响**：管理凭据是明文 Bearer；一旦监听器被错误暴露，凭据会在网络上传输。

**建议**：如果这不是有意支持的高级用法，直接拒绝非 loopback 管理监听（或要求显式的
`--allow-nonloopback-admin` 加 TLS/来源限制设计）；保留时把“必须由 TLS + 来源限制包裹”
写成可执行验收，而不是启动日志里的一句提醒。

### F-08 · P3 · `stage3b.sh` 的 note 断言与当前 truthful note 漂移（已本地修复）

**事实**：VPS 第一次跑 `stage3b.sh` 时在生成器 note 断言失败：脚本要求 note 含“未经”“OCR”，
而当前 note 已写成“历史 OCR 基线……不代表当前候选/……已完成”。这是测试文案漂移，
不是 `experimental` 或 `production_ready` 的安全回归。

**处理**：本地只改 `docs/scripts/stage3b.sh` 的断言，接受“不代表/未完成/未经”三种否定表述，
仍要求 `experimental=true`、`production_ready=false`、note 提到 OCR；运行时代码未改。
该补丁目前**未 commit**；正式候选若要包含它，需要重新生成干净 OID 与构建收据。

**建议**：把这类断言改成检查语义事实（标志位 + 风险说明），不要绑定某一句具体措辞。

### F-09 · P2 · 反代后 exampleapp 的 sameSite 只看 Host

**证据**：`cmd/exampleapp/main.go:576-600` 的 `sameSite` 在存在 `Origin` 时比较
`url.Parse(Origin).Host == r.Host`。本轮直接打 18091 且 `Host=127.0.0.1:18091` 时被
`epocha-origin-rejected`；按 18094 测试代理保留 `Host` 后成功。

**影响**：任何把 exampleapp（或其他业务后端）放在改 Host 的反代后、又只比较 `Host` 的接入，
都会在真实浏览器里失败。这不是生产验证服务的缺陷，但会让“接入示例”在反代形状下不可用，
容易被误判成 CAPTCHA 验证失败。

**建议**：生产业务后端应明确配置反代保留 `Host`，或只信任受控的 `X-Forwarded-Host` 并限制来源；
不要把测试代理当生产配方。把“公网页面 Origin、反代 Host、业务后端允许来源三者必须一致”
写进接入文档/验收。

### F-10 · P3 · `cmd/preview` 的固定高位端口测试会被测试夹具占用

**证据**：`cmd/preview/main_test.go:46` 硬编码 `127.0.0.1:18090`、`localhost:18091`、
`[::1]:18092`、`127.5.5.5:18093`。试部署的 exampleapp 占 18091、旧 18092 代理占 18092 时，
`-race` 与 engineering 都在该测试失败；释放端口后全绿。

**影响**：测试结果依赖宿主上恰好没有别的测试夹具占用这些端口；在试部署机上会制造
“看起来像代码回归”的假失败。这与 AGENTS 的“固定端口前必须检查空闲”是同一类问题。

**建议**：测试用动态空闲端口（先 `listen :0` 再取端口），或在该测试前显式检测并 `skip`
为 BLOCKED；不要把“端口被占”记成 PASS。验收脚本仍应在启动前检查固定端口。

### F-11 · P3 · 试部署夹具的卫生问题

**事实**：VPS 上还留着多组历史 headless Chromium、旧 18092 私有入口代理与测试脚本；
本轮停掉了旧 18092 代理并重启了 exampleapp（因此留言库被重置，现有 1 条本轮测试留言）。

不应继续保留。

**建议**：试部署收尾时统一清理测试夹具；生产主机上不运行这些进程。
