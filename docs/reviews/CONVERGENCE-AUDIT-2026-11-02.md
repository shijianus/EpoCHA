# EpoCHA 上线收敛复审与完整功能交付建议

审计日期：2026-11-02。审计对象：当前工作树，含已有未提交修复。本文是上一轮审计之后的复审，不把旧报告已经修复的项目重新列成开放缺陷。

## 1. 结论

**当前版本尚不满足正式上线条件，也不满足原设计的完整功能交付条件。** 已实现的 Go + SQLite 主链路和近期可靠性修复值得保留；收敛工作的重点应是修补本报告确认的剩余缺陷、完成受支持环境的真实验收，并用功能台账逐项交付原定能力。

本轮确认两个应在试部署前修复的运行缺陷：**备份会删除并非本次调用创建的同名临时文件；账本清理能力可以长期低于合法签发速度，导致过期记录无界积压。** 本轮已在工作树中实现对应防护：备份改用独占暂存目录/无覆盖发布，账本增加独立总量上限并让清理调度在有限预算内推进；聚焦回归仍需在完整 Go/Linux 门禁中复核。另复现管理凭据撤销后的在途写入边界、以变异测试确认两条 token 安全负测失真，并核实 WAL `synchronous=NORMAL` 的掉电持久化限制。

正式支持范围仍为 **B 路径（宿主静态编译后装配镜像）/ Linux arm64 / UID:GID 1000:1000**。交叉构建、Windows 可运行包、Node 模拟行为检查，均不能替代该范围的运行验收。

建议用两个清楚区分的交付结果收敛，且不删除任何原定需求：

- **受限试部署就绪**：当前已实现功能的安全性、可恢复性和接入流程经过当前候选的完整工程验收；明确仍为实验性验证服务。它不代表 CAPTCHA 抗自动解题效果或三层设计全部完成。
- **完整产品上线就绪**：除上述条件外，完成原定风险决策、多生成器权重、统计与分级淘汰、非视觉通道、管理控制台后续功能、widget 降级/备用端点等适用需求，并提供真实人工、可访问性和效果评测证据。明确列为未来评估的 Cloudflare 架构与非支持平台继续保持其原有范围。

本轮没有确认未鉴权伪造 token、跨站 secret 消费合法 token、或绕过原子一次性更新的当前漏洞；这不替代尚未完成的 Linux 全量 race 与故障验收。

## 3. 当前剩余缺陷及修复建议

优先级解释：P1 应在受限试部署前解决或形成明确的设计保证；P2 为接入、事故处置或回归可信度的重要缺口；P3 为局部测试/文档问题。本轮不因“未来功能未实现”将所有项目称为 P0 漏洞。

### C01 · P1 · Backup 清理了不属于本次调用的临时文件

**位置**：`internal/store/deploy.go:240`、`:266`、`:269`、`:272`、`:306`、`:326`。

备份最终名由秒级时间与 commit 组成，临时数据库名固定为该名称加 `.partial`。代码没有先独占认领临时文件，却在执行 `VACUUM INTO` 之前登记无条件删除它的 defer。如果同名文件已经存在，SQLite 拒绝写入后，失败清理仍会删除它。文件可能属于上一次未完成备份，也可能属于同秒并发备份。

**本轮实测**：在 `t.TempDir()` 中预先创建非空哨兵 `.partial`，调用当前 `Backup` 后得到错误，哨兵文件也被删除。证据：[`backup-observation.log`](../../release-artifacts/convergence-audit-2026-11-02-4V6N1w/backup-observation.log)。没有触碰真实备份。

同一路径还有静态可见的并发窗口：先检查最终名不存在，再 `os.Rename(partial, destDB)`；Linux rename 可以覆盖检查后才出现的目标。manifest 同样使用固定临时名，发布两个文件与错误清理之间也缺少调用所有权。最终覆盖及崩溃中断的具体形状本轮未做 Linux 实验，不能写成已复现数据损坏。

**修复建议**：用本次调用唯一、权限受控的 staging 目录/路径；只清理明确由该调用创建且仍拥有的文件。最终数据库和 manifest 采用无覆盖发布，失败时保留可诊断状态；目录同步失败不能静默宣称完整持久交付。可复用已修复 Restore 的“暂存处理、校验后无覆盖发布”思路。

**不得给在线 backup/verify 加服务数据目录运行锁**。它们必须继续允许与服务并发；需要协调的是备份输出的命名和文件所有权。

**验收**：预存非空/空 partial、预存 manifest、两个相同时间/commit 并发调用、最终目标在检查后出现、写入/同步/发布失败，均不得覆盖或删除其他调用及用户已有文件；成功产物逐份 verify，在线源库保持不变；在 Linux 上补两文件发布与崩溃恢复测试。

### C02 · P1 · 清理上限与允许签发量不匹配，过期账本可长期增长

**位置**：`cmd/server/main.go:36`、`:373`、`:380`；`internal/store/store.go:64`、`:301`、`:562`、`:597`；默认配置 `internal/config/config.go:201`。

服务每分钟调用一次 `Purge`，每轮 challenges 最多删除 500 行；活跃量准入只统计 `issued AND expires_at > now`，不统计过期/终态历史行。单次删除有界并不能保证长期数据库存量有界。

默认每站点允许 300 次签发/分钟，两个已有站点的合计允许量就可超过每分钟 500 条的清理能力。在每 IP 限制也满足、挑战随后被放弃的情况下，稳态可保持活跃记录低于默认 2000/站点、10000/全局，而过期积压持续增加。**每分钟 600 新增减 500 清理，净 100 行/分钟、144,000 行/日，仅为代码规则的算术推导，不是负载实测或磁盘耗尽时间预测。**

**本轮实测**：仅向独立测试库写入 600 条已过期挑战，一次 Purge 删除 500、保留 100；随后用 active cap=1 仍可插入新的挑战。证据：[`observed-behavior.log`](../../release-artifacts/convergence-audit-2026-11-02-4V6N1w/observed-behavior.log)。未做洪泛或压力攻击。

**修复建议**：在时间/CPU 预算内执行可持续的多批清理，必要时缩短调度间隔；并为总账本记录、数据库/WAL 使用量、清理积压建立监控与准入保护。只把 500 改为更大的固定数仍可能被合法配置超过；同样不能无限循环占住唯一写连接。

**验收**：虚拟时钟下多轮合法签发/过期/清理，包含多站点、弃答、已消费、最大 TTL、有效 response 引用；证明稳态积压有界，超预算正确拒绝且能恢复，仍有效的 response/challenge 不被提前删除，已消费或终结状态不复活；目标机测清理期间的写延迟、WAL 与图片预算。

### C03 · P1 设计保证缺口 · WAL NORMAL 不等于掉电后保留每次已确认消费

**位置**：`internal/store/store.go:80`；`docs/DESIGN.md:103`、`:106`；`docs/DECISIONS.md:159`。

当前 DSN 明确为 WAL + `synchronous=NORMAL`，消费路径确实等事务 Commit 后才返回成功。但“已提交”与“已同步到持久介质”不是同一件事。本地已锁定依赖 `modernc.org/sqlite@v1.46.1/lib/sqlite_linux_arm64.go:32993` 的 SQLite 原文说明：WAL NORMAL 的普通 commit 不执行同步，FULL 才在每次提交后同步 WAL。

因此主机掉电/操作系统崩溃可能丢失尚未同步的最近提交；如果丢失的是 `used=1` 或撤销写入，而其前置记录已持久化，重启后的一次性/撤销状态可能倒退。**本轮未做掉电实验，也没有实测该场景下 token 重放。** 进程重启、SIGKILL 或容器重建测试不能自动覆盖主机掉电语义。

这是已有 ADR 的选择，不应悄悄改配置。**推荐先补 ADR 明确部署期望，安全账本采用 WAL FULL，并在 1 vCPU 目标机量化延迟/吞吐代价**；底层存储也必须正确实现同步。若坚持 NORMAL，需要明确只保证哪些故障类型及相应重启失效策略，不能继续让运营误以为覆盖所有崩溃。

**验收**：PRAGMA 回读与所有写连接一致；普通进程崩溃和主机级故障分列；隔离环境验证已确认消费/撤销的持久性；记录备份恢复失效策略与故障语义差异，不用恢复旧快照替代运行期持久保证。

### C04 · P2 · 管理凭据撤销不阻止已经通过鉴权的在途创建

**位置**：`internal/admin/admin.go:198`、`:208`；`internal/admin/handlers.go:579`、`:587`；`internal/store/secrets.go:439`、`:444`、`:453`。

管理中间件在读取完整请求体之前鉴权，handler 随后读取 body，最后创建凭据。创建事务校验 actor 标识格式并记录审计，却不复核 actor 此时是否仍有效。

**本轮有限复现**：请求 A 已通过鉴权、等待 body；请求 B 撤销 A 所用 key 并返回 200；旧 key 的新请求得到 401；继续 A 的 body 后，创建仍返回 201，新 key 的 whoami 得到 200。证据见 `observed-behavior.log`。这是经过入口授权的在途请求，**不是匿名管理接管**。

当前文档没有定义撤销是否等待/取消在途写入，因此不把所有入口鉴权快照语义都说成漏洞。但安全事件中只撤销旧 key，不能保证这样的在途请求不再创建可持续使用的新 key。

**建议**：优先对新增/轮换凭据、提权性质的管理写入，在同一写事务中复核 actor 当前有效性并定义线性化顺序。仅在 handler 多查一次仍有查后写入窗口。同步明确“撤销成功”的在途边界；紧急停服、排空、离线 admin-recover 的事故手册要覆盖新近创建的 key。

**验收**：阻塞 body 的确定性并发测试、撤销先提交/创建先提交两种顺序、grace 到期、撤销自身、请求取消与审计；被拒写入不得返回明文或留下新增凭据。

### C05 · P2 回归可信度 · 两条 token 负测无法发现对应防线被移除

**位置**：`internal/token/token_test.go:231`、`:249`、`:329`、`:344`、`:346`、`:353`。

- `TestUnknownClaimFieldRejected` 的坏 payload 同时缺少 svid 和 mode；所谓正向对照又同时补了字段。即使不拒绝未知字段，测试仍可因缺失必需字段而通过。
- `TestSiteVersionBinding` 的“无 svid”案例实际含 svid=3，却缺 mode；局部 master 与 signer 使用的 master 不同，所以可以只在签名校验处失败。

**本轮变异证据**：删除 `DisallowUnknownFields` 后第一条测试仍 PASS；删除 Verify 的 `svid<=0` 校验后第二条测试仍 PASS。日志见 [`token-mutation-results.json`](../../release-artifacts/convergence-audit-2026-11-02-4V6N1w/token-mutation-results.json)。生产源码未改，当前两个校验仍存在；这不是现有 token 绕过结论。

**修复与验收**：从能够成功 Verify 的同一合法 token/payload 起步，每条负测只改变一个因素，使用正确签名；增加缺 svid、svid=0、负数、未知字段各自的对照。删除被测防线时，对应测试必须失败。将这种小范围变异验证用于关键防重放/来源/凭据测试，不以数量增长替代判据质量。

### C06 · P2 · 建站成功与当前 widget 可接入之间仍有操作断点

**位置**：`web/adminui/app.js:682`、`:688`、`:698`、`:751`；`docs/WIDGET.md:20`。

管理台默认创建 pow_only，当前 widget 只支持 text-image-v1 图片题；创建页不收 Origin，用户还需在详情设置精确业务 Origin、pow_question、text-image-v1、中档或更高难度并等待题池。文档已正确解释前置条件，因此不再把默认值本身当作未修复 API bug；剩下的是容易误配的产品接入流程。难度控件仍从低档开始，对图片配置需特别防止把历史 96% OCR 通过率的低档当生产默认。

**建议**：保留已有 pow_only/API 行为，增加清楚的“图片 widget 接入”配置路径和创建后检查项：精确 Origin、有效题型/难度、生成器启用、可领取水位、业务服务器的 secret、CSP 与示例代码。低档保持评测用途的明确提示，不把实验性图片包装成已生产安全认证。确认 secret 已保存之前不得通过页面跳转丢掉唯一展示机会。

**验收**：从空库、首次登录、建站、配置到真实业务写入的一条无隐藏步骤的旅程；错误 Origin/不支持模式/空池/CSP 阻断给出可操作提示，失败零业务写入；JSON 和原生表单都执行一次。

## 4. 发布与运维阻断：已执行的失败和仍缺的证据

### E01 · 当前工作目录不是合格的发布输入

[`full-gate/summary.json`](../../release-artifacts/convergence-audit-2026-11-02-4V6N1w/full-gate/summary.json) 的实际结论为 FAIL/1。唯一 FAIL 是 `go-package-inventory`：`tmp/gui-harness/main.go` 被 Git 忽略，却仍进入 `go list ./...`。本轮没有删除它。

### E02 · 正式环境的工程验收尚未完成

本机缺 Linux/arm64、GNU Make 及完整 race 环境；完整门禁正确保留 BLOCKED。没有证据支持直接把当前镜像用于正式业务。

本轮未发现“平台满足后仍必然循环失败”的新构建收据问题。当前 B 路径的参数冻结、实际二进制字节对账、镜像装配和 candidate 收据链条已经实现；人工证据缺失使 full 未完成是有意阻断，不能改成强制通过。

### E03 · 恢复接管必须在 Linux 完整目录与真实身份上验收

Restore 近期已修复为临时副本失效处理完成后再无覆盖发布，不能继续把旧恢复落位问题当作开放缺陷。但目标部署的完整数据/密钥目录接管、WAL/SHM、容器挂载、权限、锁冲突和目录同步仍缺当前实测。

必须验证：在线一致性备份；隔离恢复；新 master 且不设 previous；新管理文件与 whoami 200；旧 token/secret/admin 全被拒；站点重新配置 secret、人工启用后业务闭环；进程/容器重建后拒绝重放；切换失败保留旧现场，避免把旧库和新密钥混用。

### E04 · 公网反代与源地址信任需要目标机证据

本轮没有访问目标 VPS，也没有更改端口、防火墙、DNS 或证书。真实上线须按批准的域名/Origin/代理链验证：管理端口不公开、HTTPS、真实连接地址与受信代理头的裁决、Body 上限及超时、80/443 日志哨兵覆盖所有载体、CSP/Worker 跨源路径。`readyz=200` 不证明磁盘满时 WAL 提交一定成功，也不证明题池可用；普通 Docker 的 unhealthy 不会自动触发 restart。

### E05 · P2 · Compose 默认身份与正式支持身份仍容易配错

`deploy/docker/.env.example:28` 与 `deploy/docker/compose.yml:41` 默认使用 65534:65534，正式支持和密钥目录准备配方却是 1000:1000。`docs/DEPLOYMENT.md:43` 已要求修改，§11 的新建 .env 配方也会改成当前身份，因此这不是照完整配方仍必失败的缺陷；风险在于只复制样例或保留旧 .env 时，容器身份、密钥/数据/锁文件属主不一致。

建议提供与正式支持身份一致的发布配置，或启动前显式核对实际容器 user、目录属主及密钥可读性，给出具体修正动作；不把密钥读取/锁权限错误笼统留为 unhealthy。验收包括重跑配方不覆盖旧 .env、不覆盖密钥，旧配置身份不一致必须在真正接流量前被明确指出；65534 仍需独立运行验收才可扩大支持范围。

### E06 · 长期资源与恢复目标未得到证明

历史五分钟和当前二进制体积不能证明 1 vCPU/1GB 下稳态 RSS<100MB。建议先规定目标业务量、可接受 p95/p99 延迟、丢失窗口 RPO、恢复时间 RTO，再执行混合图片流量、低流量老化、弃答、多个站点、满图片预算、备份并发与清理积压的持续演练。24 小时可作为第一轮建议观测窗口，不是本轮已达成数字或未经授权的新验收事实。

至少采集 RSS/HWM、CPU、goroutine、SQLite 主库/WAL、账本与池水位、补题失败/退避、429/503、业务闭环成功率、备份成功时间及恢复耗时。告警应有接收人和处置步骤；日志轮转、备份保留/离机副本、密钥分离保管与证书续期需实际验证。

## 7. 优化方向及避免的返工

- **性能优先测瓶颈**：先解决积压、数据库/WAL、补池与备份竞争，再根据实际 p95/p99 决定索引、批量、连接或缓存策略；当前不需要 Redis、多实例或新框架。
- **运维优先闭合动作**：管理台先做已经有 API 的题池/审计/轮换，指标来自真实状态；健康检查不能替代写入故障和池空告警。
- **测试优先因果正确**：维持独立求解器、错误 secret 不消费、CSP/表单真实路径；用少量针对性变异确保安全断言能发现防线缺失，避免只堆测试数量。

- **配置优先安全可接入**：保留已有 API 模式，提供明确的 widget 配置入口与一次性 secret 交付，避免误开低档实验题；禁止生产“跳过验证”的开发分支。
