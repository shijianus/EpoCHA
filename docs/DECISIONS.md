## ADR-001 Cloudflare 免费计划的 Durable Objects 与边缘定位（校正）

**原表述（DESIGN v1，§2-D8 / §12 / `deploy/cloudflare/README.md`）**：
"Workers 免费版只能做无状态部分"、"Durable Objects 需要付费计划"。

**问题**：与 Cloudflare 当前官方文档相反。Workers 平台定价页写明 **Workers Free 只能创建和访问 SQLite-backed Durable Objects**，
Durable Objects 文档写明 **Free 与 Paid 计划均可使用**；免费配额为 10 万请求/天、13,000 GB-s/天、
SQL 读 5000 万行/天、SQL 写 10 万行/天、存储 5 GB。因此"必须付费"是错的；SQLite-backed DO 恰恰是免费可用的。

**现在的立场**：
- 上面那段关于"绝对不能用 CF 存状态"的论证**作废**，改为一条**工程选择**：
  **阶段 1–5 的权威验证节点是 VPS 上的 Go + SQLite，CF Worker 延后，不属于阶段 1。**
- 选择理由（与配额无关的、仍然成立的三条）：
  1. **权威性与故障域**：权威状态放在自己掌控的单进程 + 单文件 DB，备份、恢复、密钥边界都是一句话能说清的。
  2. **写配额与成本形状**：SQLite-backed DO 的免费写配额是 10 万行/天量级，付费后按行计费——把"每次验证都写"的状态放上去，成本曲线由边缘写操作决定，而源站 SQLite 在 1 vCPU 上写吞吐远高于此。这是**权衡**，不是"免费计划做不到"。
  3. **一致性模型**：DO 的单对象串行保证很有吸引力，但它会把防重放语义绑定到 CF 平台可用性上；本设计的降级要求是"源站不可用时验证失败（fail closed）"，边缘持状态会让这条更难证明。
- **重新评估触发条件**（写清楚，避免变成又一次绝对断言）：当出现"需要全球边缘低延迟签发 + 单站点日验证量 < 10 万"且愿意接受 CF 平台作为信任根时，SQLite-backed DO 是一个值得试的选项；届时先做一份"DO 内原子领题/消费"的可行性验证，再决定是否改变权威节点。
- 事实性数字（配额）必须标注来源与日期，并且在使用时重新核对——本条即为教训。

**影响**：DESIGN §2-D8、§12、`deploy/cloudflare/README.md`（阶段 5 才落地）。

## ADR-002 生成式题池的安全论证必须拆成四个独立指标（校正）

**原表述**：DESIGN §8.2 用"随机字体、扭曲、噪声、CSPRNG、HMAC、多步骤交互"以及 `rotate-v1` 的"粗 24 × 精 6 = 144"来论证题型"不可枚举/抗 AI"。

**问题**：这些是**混淆手段**，不是**安全度量**。随机性存在 ≠ 攻击成本高：多模态模型对扭曲字符的识别率不依赖题面是否随机；
`144` 只是"答案空间大小"这一个数，既没有对照实验，也没有考虑打码服务的人工兜底与模型辅助。把它写成"已验证的安全性"是错误陈述。

**现在的立场**：任何题型的安全论证必须分别给出四个正交量，且不得用其中一两个代替全部：

| 指标 | 定义 | 说明 |
|---|---|---|
| 题面随机空间 | 同一模板下可产生的**不同题面实例数**（参数 × 渲染变换的基数） | 只影响"同题复用"与缓存攻击，不影响单次求解难度 |
| 答案空间与接受容差 | 正确答案的**取值集合大小**，以及服务端接受多少比例的错误答案（容差折算） | 容差会把有效答案空间**缩小**（接受域变大），两者必须一起报 |
| 随机猜测通过率 | `接受域 / 答案空间`，不看任何求解能力的下限 | 上限由尝试次数预算封顶：`1-(1-p)^n` |
| 每次尝试成本 | 攻击者解一次题的**实测**代价（模型调用费/打码服务费/人工时间/PoW 算力），必须有测量方法与日期 | 唯一能和外部世界比较的量 |

- `rotate-v1` 的"24 × 6 = 144"**降级为未验证估算**，并在阶段 3 的验收里要求：给出该题型的四个指标数值 + 一个本地小模型/公开模型的基线通过率测量，否则不得声称安全性。
- "抗 AI"的表述统一改为："**提高每次尝试成本并限制猜测通过率**"。安全结论只允许来自 ADR-006 的成本-尝试模型，不来自题面复杂度。
- HMAC / CSPRNG / 字体随机等属于**实现约束**（防止实现自己引入可预测性），不属于对攻击者能力的论证。

**影响**：DESIGN §4 威胁模型、§8.1、§8.2 表格与其结论段；阶段 3 验收标准。

## ADR-003 答案存储：区分公开 payload 与服务端私有 verifier 数据（校正）

**原表述**：DESIGN D5——"答案一律量化为离散值 + 只存 HMAC 摘要"，并以此推导"验证只能精确匹配"。

**问题**：把一种实现手段（HMAC 精确比较）写成了对所有题型的强制约束。旋转角度、拼合、区域选择这类题本质上需要**容差验证**；
强行分桶到可精确匹配的离散值，会在容差边界上产生既不友好也不安全的裁剪（边界判错、接受域与设计不符），还可能诱导把
"正确答案的原始连续值"或其**可推导种子**放进 payload 以便客户端提交，违反更基本的原则。

**现在的立场**（原则层，具体存储方案阶段 3 定）：
1. 每题的数据分成两部分：**公开 payload**（客户端渲染所需）与**服务端私有 verifier 数据**（判分所需）。
   verifier 数据可以是摘要、参数、或任意私有结构，**只要它留在服务端**。
2. **禁止下发**：正确答案本身、任何可直接推导出答案的种子/参数（例如旋转的原始角度、生成 seed 与题面的映射关系）、
   以及能离线重放判分的秘密材料。判断标准是"拿到 payload 的人能否不求解就通过"。
3. **允许容差验证**，由题型自行决定比较方式（几何距离、区域重叠率、角度差）。连续性容差不再被 HMAC 排斥。
4. 若某题型确实可以离散化，则**摘要存储仍是首选**（它给 DB 泄露加一层），但它是**选项不是强制**。
   采用摘要存储时必须同时记录 ADR-006 之外的代价：答案空间小的题型，其摘要在活跃窗口内可被离线暴力猜测（原 R-表已含该风险）。
5. 每个题型的 verifier 方案与其四个指标（ADR-002）一起写进阶段 3 设计，并配属性测试。

**影响**：DESIGN §2-D5、§5（`pool.answer_mac` → `pool.verifier_blob` 语义）、§8.1 接口注释、§8.2 结论段。

## ADR-004 一次性消费的"安全保证"与实现手段分离（校正）

**原表述**：DESIGN §2-D2/§5 与 AGENTS 红线 3——"写者单连接串行是原子防护的**前提**，不是性能妥协"、
"`BEGIN IMMEDIATE` + `UPDATE ... WHERE status='ready'` + `RowsAffected==1` 是唯一合法写法"。

**问题**：两层错误。(a) 把**第一版的简化实现**（单连接池）说成了安全性的来源；(b) `database/sql` 的 `Tx` 已经自己发起
`BEGIN`，在 `*sql.Tx` 上再执行 `BEGIN IMMEDIATE` 是**嵌套事务错误**。事务隔离级别（deferred/immediate）是实现细节，
正确性不依赖它——依赖的是"条件状态转移 + 同事务 + 影响行数检查 + 真并发测试"。

**现在的立场**——安全保证必须同时满足这四点，任何实现都算合格：
1. **原子条件状态转移**：一条 SQL 内完成"检查旧状态 + 写入新状态"，例如
   `UPDATE challenges SET status='redeemed', redeemed_at=? WHERE id=? AND status='issued'`。
   绝不允许"先 SELECT 判断，再 UPDATE"的读-判-写回。
2. **同一事务提交**：一个业务动作涉及的多次写（消费 challenge + 创建 response）必须在同一 `Tx` 内提交；用
   `db.BeginTx` 取得 `*sql.Tx`，让驱动发起 `BEGIN`（默认 deferred），**不得**在 Tx 上手工执行 `BEGIN*`。
3. **检查影响行数**（或等价结果）：`RowsAffected != 1` 一律判失败，失败即回滚。
4. **测试证明**，而不是靠断言实现细节：(a) 同一连接池内的 N 路并发只有一个成功；(b) **两个独立 `*sql.DB` 连接**同时争抢
   同一临时 SQLite 文件，仍只有一个成功；(c) **重启进程后**重放已消费的 token 仍失败。

关于单连接：`SetMaxOpenConns(1)` 是**第一版为规避 `SQLITE_BUSY` 抖动而做的简化选择**，写清"这不是安全边界"。
需要并发读时可放宽；若驱动/SQL 模式需要特定配置（如 `busy_timeout`），**必须查文档并写测试**，不得凭记忆。

**影响**：DESIGN §2-D2、§5、§14 清单第 4 条；AGENTS 红线 3。

## ADR-005 阶段 1 就持久化防重放（范围调整）

**原表述**：DESIGN §17——阶段 1 只做 PoW+token+`/siteverify`，SQLite 与迁移放到阶段 2。

**问题**：按原计划阶段 1 只能把 nonce/response 状态放内存，阶段 2 引入 SQLite 时要**推翻并重写**消费路径与测试；
而"重启后不可重放"恰是本专案最核心的安全性质，最晚验证等于风险最大时才发现。

**现在的立场**：
- 阶段 1 引入 `modernc.org/sqlite`，做**最小**迁移：站点（配置装载）、challenge 状态、response 消费状态三张表；
  并实现 `重启后重放失败` 的测试与脚本演示。
- 完整站点管理、Key CRUD、域名白名单、限流策略配置**仍留阶段 2**。
- 阶段 1 的站点由**配置文件装载一个演示站点**；**禁止把生产密钥硬编码进代码或提交进仓库**（沿用 §6 的密钥不入库约束，
  演示密钥由脚本运行时随机生成，落临时文件，用完删除）。
- 阶段 1 只有 PoW 一层，**不得**在响应或文档里伪装存在题库或行为风控。

**影响**：DESIGN §17 阶段 1/2 验收、§16 依赖表；新增依赖见 ADR-007。

## ADR-006 数字必须标注"目标"还是"实测"；状态持久化的时序纪律（校正）

**原表述**：DESIGN §7/§13 里"浏览器 300–900ms"、"`/siteverify` p99 <60ms"、"RSS <100MB"、"≥150 req/s" 与若干容量估算混排，
读起来像已验证事实；§17 阶段 5 有"suspect 率 >15% → 自动减半/下线"的规则。

**问题**：(a) 这些数字全部**未在本机或任何 VPS 上测过**，写成指标会误导后续实现与选型；(b) 按通过率自动下线题型的规则
过于粗糙——通过率高可能只是题目太简单、或人类用户占多数，直接自动下线会造成可用性事故，也给攻击者一个"用大量失败污染统计再
诱导下线"的操作面。

**现在的立场**：
1. 凡未实测的数字，一律在文档里标注 `[目标]` 或 `[估算]`，并写明达成方式；只有带测量条件（机器、日期、负载）的数字才能写成事实。
   DESIGN §13 的表格已改为三列：目标 / 实测（待填）/ 守护方式。
2. **安全关键状态不得"先返回成功再异步持久化"**：challenge 消费、response 签发与消费必须在**事务提交之后**才产生对外可见的成功结果；
   提交失败一律 fail closed。反之，**访问统计可以异步**（丢几条不影响安全）。防重放账本不属于可异步的类别。
3. 题型淘汰改为**分级**：统计信号（通过率、时延、尝试成本、样本量）→ 先生成"候选降权"告警并保留人工确认入口；
   只有当"高通过率 **且** 极低时延 **且** 样本充足"同时成立才自动降权，自动**下线**需要额外条件（连续多窗口 + 不被更高优先级信号反驳）。
   具体阈值在阶段 5 用实测数据确定，阶段 5 之前不得实现"仅凭通过率下线"。

**影响**：DESIGN §7、§9、§13、§17 阶段 5；阶段 1 的 API 实现顺序（本 ADR 第 2 条）。

## ADR-007 依赖与工具链纪律

**新依赖**：`modernc.org/sqlite v1.46.1`（BSD-3-Clause；SQLite 本体 public domain）。
选择 `v1.46.1` 而非 latest（`v1.60.1`）的原因：`v1.46.2+` 的 `go` 指令要求 Go ≥ 1.25，`v1.60.x` 要求 Go ≥ 1.26，
而本专案在 **go1.24.5** 上开发；接受该约束等价于**隐式升级工具链**，本 ADR 明令禁止（见下）。
传递依赖（全部 permissive：BSD/MIT/Apache 系）：`modernc.org/libc v1.67.6`、`modernc.org/mathutil v1.7.1`、
`modernc.org/memory v1.11.0`、`golang.org/x/sys v0.37.0`、`golang.org/x/exp v0.0.0-20251023183803-a4bb9ffd2546`、
`github.com/google/uuid v1.6.0`、`github.com/dustin/go-humanize v1.0.1`、`github.com/mattn/go-isatty v0.0.20`、
`github.com/ncruces/go-strftime v1.0.0`、`github.com/remyoudompheng/bigfft v0.0.0-20230129092748-24d4a6f8daec`。
（这些由驱动引入，我们**不直接调用**；直接 import 只有 `modernc.org/sqlite`。）

**工具链**：`GOTOOLCHAIN=local` 固定（已写入 `Makefile`），禁止构建过程自动下载/切换 Go 版本。
不升级 Go 工具链；确需升级必须单独提出。

**已验证而非假定的事实**（用最小探针程序实测，非凭记忆）：
驱动名 `"sqlite"`；DSN 支持 `?_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)&_pragma=foreign_keys(1)&_pragma=synchronous(NORMAL)`，
连上后 `PRAGMA` 回读分别为 `wal / 5000 / 1 / 1`；linux/arm64 可编译可运行。

**未引入**：`golang.org/x/image`（阶段 3 才需要渲染）、`golang.org/x/crypto/hkdf`——标准库无 HKDF，
但本设计的派生形态是"每个用途一把固定长度密钥"，用**带域分隔的 HMAC-SHA256** 即可满足
（`K(purpose,kid) = HMAC-SHA256(master, "epocha/v1|" + purpose + "|" + kid)`，见 DESIGN §6）。
若未来出现多输出密钥/需标准 KDF 语义的场景，再单独讨论这个依赖。**不为了后续阶段提前引入依赖。**

**影响**：DESIGN §16、AGENTS 硬性技术约束。

## ADR-009 限流控制速率，控件存在量的是另一件事（阶段 1 复核新增）

**背景**：阶段 1 复核检查"challenge 签发能不能无限扩大 SQLite"时，实现只有内存令牌桶（按 `ip` 与 `site_key` 两维），
文档 §9 也把它写成滥用防护的全部。

**问题**：三层错误。
1. **速率 ≠ 存量**。把 rpm 配得再低，只要攻击者有足够多源地址（IPv6 / 代理池），库里同时存在的活动 challenge 行数
   就没有上界——限流器保护 CPU，保护不了 50GB 磁盘和 `count(*)` 的扫描成本。
2. **站点维度按自报字符串计数**。`site:<调用方传入的 site_key>` 让任何人能为不存在的站点创建限流条目；
   状态条目到硬上限后按最旧淘汰，于是**真实站点的计数会被反复冲掉并归零**——防护反向变成绕过口。
3. **清理任务与外键冲突**。`Purge` 先删 responses（`used=1 OR 过期`）再删 challenges（`status<>'issued' AND 过期`），
   但"被兑换、尚未验证、且 response TTL 长于 challenge 剩余寿命"的组合下，删 challenge 触发
   `FOREIGN KEY constraint failed`（实测报错），清理从此永久失败、账本只增不减。

**现在的立场**：
- **速率**与**存量**分别设界，且存量判定必须在写入的同一条 SQL 内完成（与 ADR-004 的"条件状态转移"同一手法）：
  `INSERT INTO challenges … SELECT … WHERE (SELECT count(*) FROM challenges WHERE status='issued' AND expires_at>?) < ?`，
  全局与单站两个条件同时判定，`RowsAffected != 1` 即 `ErrCapExceeded`，对外折叠为 429。
- 站点维度限流的 key 一律取**库中站点 id**；未知 site_key 只消耗来源地址维度的额度，不创建站点条目。
- `Purge` 必须与外键相容：challenge 仅在**没有任何 response 行再引用它**时删除；每批行数有上限（500）；
  两条删除放同一事务。清理永远不删除"仍有效的未消费 response"——防重放窗口的长度由 TTL 决定，不由清理任务决定。
- **删除行不等于文件缩小**：SQLite 只把页放进空闲链。任何"库体积受控"的表述必须区分行数与字节数，
  且这一事实由测试固定（`TestPurgeFreesPagesNotFileShrink`）。收缩需 `VACUUM`，本版不做（单写连接长时间独占）。
- TTL 必须有上界：有效期直接等于"为了防重放必须保留多久"，无上限的配置项就是无上限的磁盘增长器。

**影响**：DESIGN §9（新增"速率与存量"段）、§5.1（Purge 语义）、§6（payload 上限按实现取严者 2048B）、
§14-6/§14-9；`internal/store`（`Caps`、`ErrCapExceeded`、`Purge`）、`internal/api`（限流顺序、错误码族）、
`internal/config`（4 个新校验/配置项）、`cmd/server`（purge 关闭路径）。

## ADR-010 阶段 2：权威数据源、旧列中和、站点版本与撤销的表示法

**背景**：阶段 2 要引入多站点管理、密钥生命周期、来源策略与审计，同时必须能升级现存的阶段 1 库。

**遇到的问题与决定**：

1. **配置文件与数据库谁说了算**。阶段 1 的 `PutSite` 每次启动都 `ON CONFLICT DO UPDATE`，把配置里的
   secret/难度**覆盖回库**。这在阶段 1 无害（库只有配置这一个来源），但一旦有了管理 API，
   它就变成安全缺陷：运维在 API 里撤销的密钥、停用的站点会被下一次重启悄悄恢复。
   → 立场：**SQLite 是站点与策略的唯一权威数据源**。`--sites`/`EPOCHA_SITES_FILE` 降级为
   **显式的一次性导入**入口：`site_key` 已存在于库中时该条配置完全不生效（`store.ImportSite` 返回 `imported=false`）。
   有测试同时钉住"重启不复活已停用站点"与"重启不复活已撤销密钥"。
   *代价*：配置文件改了 secret 却没有任何效果，运维可能误以为改成功了 → 启动日志明确打印"站点已在库中，配置条目不生效"。

2. **`sites.secret_mac` 删不掉**。实测（modernc 内置 SQLite 3.51.2）`ALTER TABLE ... DROP COLUMN` 对带
   UNIQUE 约束的列报 `cannot drop UNIQUE column`，而阶段 1 的列定义正是 `secret_mac TEXT NOT NULL UNIQUE`。
   备选方案与结论：
   - 表重建（12 步法）需要 `PRAGMA foreign_keys=OFF`，而**该 pragma 在事务内是 no-op**（SQLite 文档），
     意味着迁移要在事务外做、崩溃时留半状态；且 `challenges`/`responses` 的外键指向 `sites`，
     删父表会触发 FK。风险大于收益。
   - 留着原值不动 = 留下**第二个真相源**：将来任何一段误读它的代码都会让"已撤销的凭据"重新可用。
   - → 采用**中和**：迁移把原摘要搬进 `site_secrets` 后，把旧列改写为
     `HMAC(pepper, "epocha/v1|retired|" + 旧摘要十六进制)`。它不可能等于任何 `HMAC(pepper, secret)`，
     长度与形状仍是 64 hex（不破坏 UNIQUE 约束），且因为输入含旧摘要而天然跨行唯一。
     新建站点写的是 `sha256hex("epocha/v1|retired|" + site_key)`——同理不可用于认证。
     有测试直接断言"旧列不等于任何可用摘要"。

3. **撤销怎么表示**。备选：状态列（`status IN ('active','revoked')`）+ 后台任务把"过渡期到期"的行改成 revoked。
   → 采用**单一时间戳 `revoked_at`**，有效性 = `revoked_at IS NULL OR revoked_at > now`。
   "立即撤销"写当前时刻，"过渡期"写 `now + grace`（上限 86400 秒）。
   理由：不需要任何后台任务或额外状态机，判定纯读库，**重启与崩溃后语义完全一致**；
   过渡期到期是自然发生的，不依赖清理任务的调度是否健康。

4. **站点版本进入签名**。需求是"停用前签发的未消费 token 不会因为重新启用而复活"。只靠 `enabled` 标志
   在请求时判定也能做到"停用期间不放行"，但**重新启用后**那些 token 又会重新可放行。
   → 在 token claims 里加 `svid`（签发时的 `sites.version`），启停各提升一次版本并在 redeem/siteverify 复核。
   *代价（明确记录）*：升级后旧主密钥签发的**阶段 1 token**（没有 `svid` 字段）一律被拒；
   影响窗口不超过 TTL 的 1 小时，且账本里的"已消费"状态完整保留——失效方向是"更严"，可接受。

5. **摘要算法的域分隔出现一个例外**。红线要求派生与摘要都带域分隔，但站点 secret 的摘要必须
   **保持阶段 1 的 `HMAC(pepper, secret)` 原样**，否则 `0002` 迁移搬过来的旧摘要全部对不上，
   升级即等于把所有站点的密钥作废。管理凭据是新引入的，所以它单独使用
   `HMAC(pepper, sha256hex("epocha/v1|admin|" + key))`。
   → 立场：**迁移兼容性优先于形式统一**，但两者不可互换这条性质仍然成立（测试覆盖），
   并且不引入任何自创算法——两个都是标准 HMAC-SHA256。

6. **`key_id` 是公开的、与 secret 分离的标识**。secret 里**不含**任何 id 段：`/siteverify` 仍然用
   "对提供的 secret 求一次摘要、与全表常数时间比较"的方式定位站点，`key_id`（`k<12 hex>`）只用于
   管理面寻址与审计 target。迁移行的 `key_id` 用确定性的 `legacy-<site_id>`（阶段 1 每站点只有一把），
   而不是从摘要截取前缀——**截断 MAC 等于公开其前缀**，会把在线/离线爆破的判定空间缩小。

7. **管理监听的隔离方式**。阶段 1 复核后确认：把管理路由挂在公共 mux 上再做鉴权，等于把"忘了配凭据"
   变成"公开暴露一个永远 401 的面"，也让反代配置错误直接变成攻击面。
   → 管理路由**只存在于 admin listener**（默认 `127.0.0.1:8081`）；公共 listener 的路由表里没有这些路径，
   从公共端口打过去是 404。测试断言的是"404 而不是 401"，因为这个差别正是隔离是否真实存在的证据。

**影响**：DESIGN §5.3（新增）、§6、§10.2、§10.3、§12、§15、§17 阶段 2；
`internal/store/{sites,secrets,origins,audit}.go`、`migrations/0002_stage2.sql`、`internal/admin`、
`internal/api/handlers.go`（来源与 CORS）、`cmd/server/main.go`（双监听器）、`internal/config`。

## ADR-011 阶段 3A：题池模型、单次作答终结与答案的摘要存储

**背景**：3A 要建立生成器 + 预生成题池 + 原子领题 + 一次答案提交，并通过既有的 PoW → redeem → siteverify 流程。
DESIGN §8.3 的题池草案写于阶段 0，几处细节在实现时必须定形或被证明不合适。

**决定与理由**：

1. **站点显式模式，而非"有题就出题"**。`sites.verify_mode ∈ {pow_only, pow_question}`，迁移默认 `pow_only`。
   理由：模式是业务方契约的一部分（改模式会让现有集成拿到的响应形状变化），绝不能因为"池里刚好有题"而自动变化。
   `pow_question` 只能通过管理 API 显式设置；阶段 2 的"重启不把配置覆盖回库"语义同样适用于这里。

2. **`Redeem` 与"答案对不对"绑在一个事务里，但答案的判定必须在 store 之外**。
   `store.RedeemAttempt(ctx, cid, now, ttl, verdict)` 接受一个已经算好的判定结果：
   `verdict=correct` → 条件置 `redeemed` + 建 response；`verdict=wrong` → 条件置 `invalid`（终态）。
   **两条分支都在同一事务里提交，且 wrong 分支绝不返回 error**——否则一次 `error` 让整笔事务回滚，
   challenge 回到 `issued`，攻击者就能对同一道题无限重试（这正是本轮要做故障注入回归的点）。
   判分本身（HMAC 比较）在 API 层完成：它不需要写库，放进写事务只会拉长持锁时间。
   判定顺序（3A 定稿，取代我最初的草稿"先判 PoW"）：**token → 站点/来源 → 答案文法 → PoW → 终结性作答**。
   `verdict` 在 PoW 之前就算出来了，但**状态变更在 PoW 之后**，所以顺序不影响终态；把它写成"先判 PoW"
   会让读者以为存在一个"PoW 通过但答案还没判"的窗口，实际不存在。

3. **一次作答**：`pow_question` 下 challenge 只有一次有效答案尝试机会（正确→签发，错误→终态作废）。
   DESIGN §3 原来的"累计 3 次失败作废"保留给 `pow_only`（PoW 解错的场景，且那条路径行为不变以免破坏阶段 1/2 验收）。
   界定"有效尝试"：**结构畸形与非数字答案不算**（返回 400 `invalid-request`，不改状态），
   文法正确但数值错误才算；PoW 不对也不算作答（走 `FailAttempt`，不进终结事务）。
   代价如实记录：被 PoW 失败累计作废的 `pow_question` challenge，其绑定的题**不回池**（invariant #2 优先），
   而是随题目 TTL 到期被清理——用一条容量换"同一题面绝不面对第二个挑战者"。

4. **答案不落库明文，改用带上下文的摘要**。红线 5 禁止答案明文入库，而算术题答案是可离散化的
   （ADR-003 明确"可离散化时摘要是首选"）。**实现形态**（与本文最初的草稿不同：原稿写的是
   `HMAC(K_q, pool_row_id || "\0" || 答案)`，定稿改为**每题随机 nonce**，因为 row id 由 `INSERT` 前生成的 id 决定、
   且把行标识当密码学上下文用是不必要的耦合）：
   `verifier_blob = nonce(16B) || HMAC(K_q, "epocha/v1|qver|" || nonce || 0x00 || 规范化答案)`，
   `K_q = token.DerivePurpose(master, "qver") = HMAC(master, "epocha/v1|qver|" + kid)`
   （DESIGN §6 的域分隔派生，**不引入新密码学原语**、不加 HKDF、不改 HMAC 结构）。
   为什么带 per-题 nonce：只读到库的人无法用"摘要相同"免费聚类出"这些题同答案"，
   同时轮换 `kid` 会让所有历史 verifier 失效——这正是期望语义（密钥泄露后旧题目摘要不该继续可用）。
   总长 48 字节，被 `MaxVerifierBytes=512` 与库内 CHECK 双重限制。
   诚实记录的残余风险：答案空间小 + 摘要在库内 ⇒ **同时拿到 DB 与主密钥**的人可在题目 TTL 内离线枚举；
   这正是 §4 已列的"活跃题目可被离线暴力猜测"，不是新增风险，也再次说明 pepper 与主密钥必须与库分离存放。

5. **公开 payload 用明确类型 + 允许字段列表**，不依赖 `json:"-"`。
   生成器返回 `PublicPayload`（具名结构体）与 `PrivateVerifier`（字节）两个独立值；
   落库时 `payload_json` 只来自公开结构体的序列化，`verifier_blob` 只来自私有值；
   出网时 API 再用自己的 DTO 结构体（`question` 字段白名单）重新编码。
   为什么不只用 `json:"-"`：那是"字段级抑制"，一旦有人新增字段忘了打标签就静默泄露；
   两道具名类型 + 一个"键集合必须等于白名单"的测试比标签可靠。
   **算术题面本身可被程序求值**，所以绝不写"答案不可从 payload 推导"；
   这里保证的只是"payload 里没有额外的答案字段、没有私有 verifier、没有内部种子"。

6. **领题与 challenge 创建同事务，生成不在事务内**。
   `IssueChallengeWithQuestion` 在一个 `BeginTx` 里：插 challenge 行 → `SELECT` 一个候选 `pool.id`
   → `UPDATE pool SET status='assigned', challenge_id=? WHERE id=? AND status='ready' AND expires_at>?`
   并检查 `RowsAffected==1`（ADR-004 的手法）→ 回读题面。**候选 SELECT 在事务内**（本文最初的草稿写的是
   "事务外 SELECT 候选"，实现后确认放事务内更简单且同样正确——判定权在条件更新，不在 SELECT 的位置）。
   领取条件还要求 `pool.expires_at > challenge.expires_at`：题目不能比绑它的 challenge 先过期，
   否则会出现"challenge 还有效但题已过期"的死角（这条一度让种子题永远领不到，是本轮实测踩到的）。
   池里没有满足条件的题 ⇒ 事务回滚，**challenge 行也不留下**（不会凭空消耗一份 challenge 存量）。
   *为什么不用 `UPDATE ... WHERE id=(SELECT ...) LIMIT 1`*：SQLite 的 UPDATE 不支持 LIMIT（子查询形式虽可行，
   但可读性与错误定位更差），且唯一性由条件更新 + 影响行数保证，不需要 LIMIT。

7. **池空不降级**。返回 503 + 文档化码 `challenge-unavailable` + `Retry-After`，由后台 worker 补题。
   这**偏离** DESIGN §8.3 的"池空时同步生成 + pool_miss 计数"：同步生成会把不可控的 CPU 成本塞进
   公开请求路径（1 vCPU），而 3A 还没有渲染成本可测。阶段 3B 若引入图片题再评估是否恢复同步兜底。

8. **池按 (generator_id, version, difficulty) 分桶，不按站点分桶**。
   理由：题目内容与站点无关，站点差异只在策略（选哪个生成器、哪档难度）；按站点复制会让
   水位与容量随站点数线性膨胀。隔离粒度必须覆盖策略维度，否则会把不合适的档位发给站点。

9. **终态与清理**：`ready → assigned → terminal`，assigned **永不回 ready**（断线、超时、答案错误都不回池，
   这是 invariant #2 的落点——回池等于让同一题面对多个挑战者，破坏"一题一挑战"）。
   清理规则同时修掉阶段 1 遗留的一个体积问题：`challenges` 原先只删"非 issued 且过期"的行，
   于是被放弃的 issued 行永不消失。新规则是"过期即可删（任何状态），前提是没有 response 行引用它、
   **也没有 pool 行绑定它**"；删除顺序固定 `responses → pool → challenges`（反了就会被外键永久卡住，
   阶段 1 的 ADR-009 就是这个 bug 的教训）。
   安全性不变：删除过期行只会让判定更早走到 fail closed，不会让已消费 token 重新可用（有测试钉住）。
   代价如实记录：被 PoW 失败累计作废的 `pow_question` challenge，其绑定题要等到**题目 TTL 到期**才离开库里，
   期间它占着池容量但不可能再被任何人领走。

10. **池水位沿用 DESIGN §8.3 的量级，但 3A 用常量而不是按站点数动态计算**：
    `low=50`、`high=100`、`max_rows=20000` 全部标注 `[目标]`。
    §8.3 的 `clamp(2*站点数, 50, 500)` **没有实现**——"按站点数"要求回答"站点数变了怎么办、按活跃站点还是全部站点、
    软吊销的站点算不算"，这些都是阶段 5 的运维面问题，3A 不猜答案。生成并发固定 1（`MaxWorkers=4` 封顶），
    每补 10 题 sleep 100ms 让出 CPU。

11. **两条只在实现后才看得见的资源约束**（都属于"不测就不会想到"的一类）：
    - **每题熵读取上限 4096B**（`io.LimitReader`）。测试注入一条"每次返回相同字节"的熵源时，
      `crypto/rand.Int` 的拒绝采样会**永久自旋**——本轮实测把测试挂死 5 分钟。生产路径同样必须有界：
      熵源变畸形应当变成一次可退避的失败（`ErrOutOfEntropy`），而不是把 worker 变成不可取消的忙循环。
    - **水位迟滞 `refilling`**。一批补不完（`BatchPerTick` < 缺口）时，"补到 low 就停"会让池长期停在低位
      （下一轮检查立刻又低于 low）。置位/撤除分别绑定 low/high 两个阈值解决。
      它是内存态：重启最多晚一轮或多补一轮，**不参与任何安全判定**，这一点写进 §8.3 而不是藏在代码里。

12. **主密钥轮换与题目 verifier**：`K(qver)` 只由当前主密钥派生，**不做双密钥兼容**。
    后果是轮换后存量题的摘要在新密钥下必然判假（即使答案正确）——fail closed，有测试
    （`TestVerifierFailsClosedAfterKeyChange`）。代价换成"不给生成器再加一层密钥指纹结构"，
    并把"轮换前先清池"写成运维程序（DESIGN §6），而不是在实现里假装这个问题不存在。

**影响**：DESIGN §5.4（新增）、§8.4（新增）、§10.1（`challenge`/`redeem` 响应形状与 `challenge-unavailable`）、
§10.2（模式与池状态接口）、§17 阶段 3A；`internal/generator`（契约补齐）、`internal/pool`（实现）、
`internal/store`（`RedeemAttempt`、领题事务、池行与清理）、`internal/api`、`internal/admin`、`migrations/0003_stage3a.sql`。

## ADR-012 阶段 3B：图片资产的存放与传输形态、字节预算、不新增裸媒体端点

**背景**：3B 要引入第一个视觉题型，于是第一次面对"题目不再是一段文本，而是一份二进制资产"。
DESIGN §5.2 的草稿里 `pool.asset_blob BLOB` 与 §10.1 的 `GET /asset/<pool_id>/<sig>` 是两条**互相冲突**的路线，
必须选一条并说清代价。

**决定与理由**：

1. **PNG 存 SQLite BLOB，与题目同一行**。理由三条，都是可验证的性质而不是一般偏好：
   (a) 生命周期与题目行天然一致——清理任务删 `pool` 行时资产一起消失，不存在"孤儿文件"要扫，
       也不需要路径清理、权限位、文件名脱敏这些新攻击面；
   (b) 权威存储仍然只有一个（DESIGN D2/ADR-001 的故障域与备份边界纪律），不新增一套一致性证明；
   (c) 领取与判分本来就在同一个库里，多一个存储就多一处"谁是真的"。
   **代价**：库体积随图片增长，于是"行数上限"不再足够——见第 4 条。

2. **图片通过公开 DTO 以 base64 内联下发，不新增可枚举的裸媒体端点**。
   §10.1 草稿的 `/asset/<pool_id>/<sig>` 意味着：一个题目标识要变成客户端可见的、可猜测的输入，
   于是要加签名、加防枚举、加"这个 asset 是否属于那张 challenge"的绑定校验，
   而且缓存语义（`no-store` 之外还要防 CDN）也得重做一遍。3B 的题目是**一次性**的，
   内联让"图只跟着它那张 challenge 出去一次"成为结构事实——没有第二条路径可以拿到它。
   代价：单次 `/api/challenge` 响应从 ~0.5KB 变成 ~8KB（d5 实测 7,964 字符 base64），
   且图片不能被浏览器单独缓存或懒加载。这一代价换掉的是整个"媒体面"的安全证明义务。
   *未来若真要省带宽*，再单独评估签名 URL，而不是现在顺手加一个开放端点。

3. **资产与判分彻底解耦**：判分路径只 SELECT `verifier_blob`（`QuestionVerifierForChallenge`），
   领取路径是唯一把 `asset_blob` 读进 Go 的地方且一次只读一行。
   于是"资产被清理/损坏 ⇒ 正确答案判假"这类静默事故在结构上不可能发生（测试把资产置 NULL 后仍兑换成功）。
   资产与 MIME 必须成对：只有一半的记录要么下发成空白题面、要么让浏览器猜类型，两者都拒绝（fail closed）。

4. **字节预算与行数上限是两条独立的边界，且都在写入的同一条 SQL 内判定**。
   一条图片题的字节可以是算术题的上百倍（实测 6,315B vs 63B），只看条数就等于没有容量控制。
   沿用 ADR-009 的手法：`INSERT … SELECT … WHERE (SELECT count(*)) < ? AND (SELECT sum(length(asset_blob))) + length(?) <= ?`，
   不靠"先查再插"。`MaxImageBytes=0` 的含义是"禁止任何图片资产"而不是"不限"——
   把零值解释成无限会让一个漏填的字段变成无界磁盘增长器（同一条理由也给了预算的上界 1 GiB）。
   worker 侧另有一次**预检查**（`sum(length(asset_blob)) + 单题上限 > 预算 ⇒ 跳过该桶`），
   它不是判定（判定仍在 SQL 里），作用是**别白烧一次渲染**：否则预算耗尽后每轮都会生成一张被拒的图，
   在 1 vCPU 上这就是一个自造的 CPU 放大面。

5. **统计绝不把 BLOB 读进 Go**：字节数一律用 SQLite 聚合 `sum(length(asset_blob))`，跨进程边界的只有整数。
   1GB 目标机上"把上千条 64KB 资产读进内存算总和"是一个真实可发生的内存事故，而它写在 Go 代码里时看起来很正常。

6. **图片不是秘密，文档不许这么说**。图里可见的字符本来就要给答题者看：本轮保证的是
   "答案明文不落库/不下发为可机读文本/不进日志、PNG 无文本元数据块、DTO 只有白名单字段"，
   而不是"图片内容不可识别"。`production_ready:false` + `experimental:true` 是这条认识论的落点：
   M4（每次尝试成本）未测 ⇒ 任何"抗 AI/抗 OCR"的表述都是无证据声明（ADR-002）。

7. **生成器禁用采用进程级白名单**（`EPOCHA_GENERATORS`）而不是数据库里的开关。
   理由：题型是否可用取决于**这个进程里有没有它的判分实现**，那是二进制的事实，不是站点配置的事实；
   把它放进库就会造出"库里说开着、代码里没有"的第二种真相。
   语义：禁用 ⇒ 不再备题、指向它的站点 503（不降级）；**已签发**的题目判分时找不到生成器 ⇒ 同样 503 且
   **不消耗作答机会**（状态不变，重新启用即可继续）。白名单里写错一个名字直接拒绝启动——
   静默忽略会让运维以为"已经关掉了"，那比没关更危险。

**未做（并说明为什么不做）**：对象存储/文件落盘（多一套一致性、路径脱敏与权限面）、
CDN 与图片缓存（一次性资产没有可缓存语义）、为省带宽做签名 URL（第 2 条的代价还没到必须付的时候）、
自动淘汰题型（ADR-006 要求分级 + 人工确认，属后续阶段）。

**影响**：DESIGN §5.5（新增）、§8.5（新增）、§10.1（图片 DTO 与"不采用 /asset 端点"）、
§10.2（experimental/production_ready、池的字节观测、禁用语义）、§13（图片资产与磁盘/RSS 实测）、
§16（`golang.org/x/image` v0.36.0）、§18（R13/R14）；
`internal/store/migrations/0004_stage3b.sql`、`internal/store/pool.go`（`PoolLimits`、`ImageAssetBytes`、
`QuestionVerifierForChallenge`）、`internal/pool`（图片桶水位/预算/让步）、`internal/api/handlers.go`、
`internal/admin`、`internal/config`、`cmd/{preview,evalgen,evalocr,devseed}`、`internal/eval`、`web/preview`。

## ADR-013 阶段 4A：widget 的挂载方式、worker 的两条路径、PoW 的跨实现一致性证明

**状态**：已采纳（2026-10-18）

### 背景
阶段 4 要把"用户在浏览器里完成一次验证"变成真的：组件要能被任意业务页面嵌入、要在页面里算 PoW、
要与服务端的来源策略/预检/一次性语义严丝合缝，并且**不能**为了"能跑"放宽任何一条安全约束。

### 决策

1. **直接 DOM/Shadow DOM 挂载，不引入 iframe。**
   Shadow DOM 只隔离样式与命名，**不是安全边界**——同源脚本照样能读它、改它，文档与代码注释都必须这么写。
   选它的理由是嵌入方样式冲突与多实例隔离，不是安全性。
   **不用 iframe 是刻意的**：iframe 会换 Origin，之后很容易滑向"让页面自报父域名当作可信来源"，
   而 §10.3 的来源裁决依赖浏览器强制设置的 `Origin` 头；一旦引入第二套"自报来源"就有两种真相。

2. **PoW 在 Dedicated Worker 里算，两条加载路径都实现。**
   A) 主脚本内嵌同一份 worker 源码，运行时建 Blob Worker（需要接入页 `worker-src blob:`）；
   B) 接入方把 `v1.worker.js` 与页面**同源**部署，用 `workerUrl` 指定（只接受同源 URL，否则 `throw`）。
   两条路径跑的是**逐字节相同**的源码——`web/widget/widget_test.go` 与 Node 侧向量测试各钉一次，
   因为"两份拷贝分叉"最坏的情况是同源路径跑到一份没测过的代码上。
   禁止项写进实现与测试：不用 `eval`/`new Function`/动态 `import`，服务端 challenge 不能指定可执行脚本 URL，
   CSP 挡住 Worker 时给 `worker-blocked` 明确失败——**不**回落到主线程"假装算完"，也**不**假装验证完成。

3. **纯 JS SHA-256，并且用"跨实现共享的固定向量"证明它是对的。**
   `crypto.subtle.digest` 每次摘要都要跨一次异步边界，实测吞吐只有千级/秒：bits=18（期望 26 万次）要几十秒，
   唯一"解决"办法是降低服务端难度——那是红线。自写 SHA-256 的代价是"两套实现必须等价"，
   于是把事实钉成一个文件：`internal/pow/testdata/pow_vectors.json` 由 **Go 实现**生成并断言
   （实现被改动 → 文件变红），Node 侧用 worker 的**原始字节**在 `vm` 里断言同一份文件
   （JS 改动 → 断言变红）。两端各自对着同一真值，差异在任一侧都会显形。
   这条不是形式：本轮它抓到手抄 K 表 10 个常量写错、Σ0 用了 ROTR18 而非 ROTR22 ——
   两个"两端各自跑自己的测试都能通过"的缺陷。

4. **有效期以服务端为最终依据，客户端倒计时只为体验。**
   `/api/challenge` 与 `/api/redeem` 本来就返回 `expires_in`（题目 TTL 与 response TTL 是两个不同值），
   widget 直接用它们；**没给就不设倒计时**，不猜"所有 token 固定两分钟"。过期时**清空 token**
   （`getResponse()` 返回空串、隐藏字段一起清），不只是改 UI；标签页从后台恢复时立刻复核 deadline。

5. **`site_key` 一致性是新增的公开面约束，方向是收紧。**
   JSON 请求触发 CORS 预检，而预检看不见请求体 ⇒ 服务端只能从 URL（或 `X-Epocha-Site-Key`）认站点。
   若实际操作改读请求体，就出现"预检按 A 站授权、落到 B 站"。规则：**URL 与体（redeem 时是 URL 与 token 所属站点）
   必须一致**，不一致一律 400 `invalid-request`；同一参数出现多个不同值也算冲突。
   刻意**不**实现"以某一处为准"——选哪一处都会留下一条可被利用的歧义。
   检查排在任何状态消费之前：被拒的 redeem **不得**消耗受害者唯一的作答机会（有测试钉住判定顺序）。
   不带 URL 参数的非浏览器客户端行为不变（阶段 1/2/3A/3B 的脚本与 devclient 全部回归通过）。

6. **业务授权只由服务端判定。**
   `cmd/exampleapp` 故意让"提交留言"按钮一直可点：没有 token 也发得出请求，服务端必然拒绝并零写入；
   `onSuccess` 只是 UI 信号。同时示例后端固定验证目标（启动时决定，请求体里出现 `target/url/secret` 一律 400），
   验证服务宕机/超时/5xx 一律 fail closed；**token 已被消费但业务写入失败**时提示重新验证、不缓存那次成功
   （否则等于绕过一次性语义）。

### 未做（以及为什么）
- 音频/其他非视觉等价通道：只有视觉通道的 CAPTCHA 对无法看清图片的用户就是不可完成，这是产品缺口，
  不能用"PoW-only 降级"糊过去（少掉的是"题目"这一层，防线含义不同）。
- 服务端签发过期时间的**新字段**：两个端点已经返回 `expires_in`，再加字段只是扩大兼容面。
- SRI/`integrity`：同源自托管不需要；经第三方 CDN 分发时接入方应自托管或自行加 SRI（文档写明）。
- 用 iframe 的隔离方案：见第 1 条，它带来的不是一个安全边界而是第二个"来源真相"。

### 影响
- 新增生产路由 `/widget/v1.js`、`/widget/v1.worker.js`（只读、白名单资源名、`nosniff`、可缓存、无 CORS 头）。
- `web/widget/` 从"目录约定里的占位"变成实际交付；`cmd/exampleapp` 与 `docs/scripts/browser/` 加入目录约定（开发期）。
- 验收口径变化写进 AGENTS.md：三态（PASS/BLOCKED/NOT_RUN）、退出码分层、门禁不嵌套总门禁。

## ADR-014 阶段 5A：备份一致性方案、保守恢复的语义、密钥文件入口与容器边界

### 背景

DESIGN §12 原先把备份写成"`sqlite3 .backup` 每日 + WAL checkpoint"，§6 把主密钥入口写成
"`EPOCHA_MASTER_KEY`（32B，env 或 `--master-key-file`）"。两条都从未实现，而阶段 5A 要交付
能在 1 vCPU / 1GB 单机上真的跑起来的部署包，这两处必须落到可执行的形式。同时"部署验收"很容易
被写成"文件都齐了"，而真正的验收问题是：**这份快照是不是完整的、这份恢复会不会把撤销过的东西放回来、
这台机器在限额内的形状是什么**。

### 决策

1. **备份主方案是 `VACUUM INTO`，不是 `cp`，也不是 `sqlite3` CLI。**
   库跑在 WAL 模式（DSN 钉住），最新那段状态在 `-wal` 里；DESIGN §13 自己就记着实测形状
   "写入进行中主文件 4,096B + WAL 2,855,192B"。**只 `cp` 主文件会得到一个存在但落后的库**，
   而且看起来是成功的。`sqlite3` 是外部二进制，与"服务与运维能力都用纯 Go"冲突（AGENTS 硬性约束），
   所以本条**更正 DESIGN §12** 而不是照做。
   SQLite backup API（在线）本轮不选：驱动层是否暴露该能力没做逐调用验证，而本轮要的是**可证明**的方案。
   `VACUUM INTO` 的四条依赖事实由 `internal/store/capability_test.go` 钉住 `modernc.org/sqlite v1.46.1`
   的真实行为（只读连接可执行、目标名走绑定参数、未 checkpoint 的 WAL 内容进快照、失败不留半成品）。
   任何一条哪天不再成立，方案就必须换成"停服冷备份"，而不是继续假装 `cp` 安全——
   这与 AGENTS 里"能力边界必须由能力测试给出"是同一条教训的第二次应用。

2. **恢复是"保守恢复"：产物是新文件，且快照里所有还能被接受的东西一次性失效。**
   旧快照**不**保持备份之后发生的消费、撤销与停用记录——这是快照的定义，不是可以小心绕过的风险。
   因此一条事务里做：`challenges` 全部置 `invalid`、`responses` 全删、`pool` 全删、`sites` 全部 `enabled=0`、
   `site_secrets` 与 `admin_keys` 全删，然后装入**本次操作指定的新管理凭据**并写一条审计。
   明确**拒绝**"温和恢复"（保留旧凭据只标记来源）：那等价于"被撤销的凭据复活"，
   而本服务的安全语义（ADR-004 的一次性消费、§6 的凭据生命周期）不允许这种回退。
   连带后果如实写进文档而不是淡化：**恢复 = 全部接入方的 `secret_key` 需要重新签发**。
   主密钥不在库里，所以恢复后的启动要求是"用新的 master，且不设 `EPOCHA_MASTER_KEY_PREVIOUS`"——
   previous 那把签名回退正是"旧 token 重新可用"的唯一通道。
   pepper 与备份的配对用单向指纹（域分隔 `epocha/v1|pepper-fp|`）在恢复前检查；
   不配对默认拒绝，只有显式 `--rotate-pepper` 才继续（拿错密钥文件与有意轮换在两可之间，靠猜的失败面是摘要与签名）。

3. **密钥入口增加 `*_FILE`，且 env 与 `_FILE` 同时非空即拒绝启动，不做优先级。**
   存在的理由是容器里 env 的泄露面：`ps`、`docker inspect`、编排平台 KV、CI 日志都会原样带出环境变量。
   "文件优先"或"env 优先"都会制造"运维改的那一份不生效"这类极难定位的故障；
   拒绝启动比静默选一份安全，因为配错的失败面是签名与摘要。
   文件校验落在 **`os.Stat` 解析后的目标**上（secret 挂载本身就是指向 `..data/<uuid>` 的符号链接，
   拒绝符号链接等于否掉这个入口的主要用法）：目标必须是普通文件、group/other 权限位必须为空、
   非空且 ≤4096B（**达到上限即失败，不截断**）。错误文案只给入口变量名与失败类别——
   内容本身就是密钥，路径会原样出现在启动日志里，两者都不进文案。

4. **`/readyz` 与 `/healthz` 分列，且就绪判据包含"写路径可用"。**
   "每次验证都失败"的实例完全可能同时是活着的（WAL 库读得动但目录只读、磁盘满、迁移没跑完）。
   写可用性用两个零副作用的文件级检查表达（主文件可 `O_WRONLY` 打开 + 数据目录可 `CreateTemp`），
   **不用** `BEGIN IMMEDIATE`：连接池上限是 1（`SetMaxOpenConns(1)`），探针占住那条连接会把正常流量排在后面——
   探针不该自己成为故障源。题池水位低**不是**未就绪（那是容量信号，业务侧本来就是 503 + 不降级），
   把它当就绪判据会让编排在整个补池期间反复重启服务。
   响应只回 `ready`/`unavailable` 一词；原因只进日志的类别字段（红线 8）。

5. **管理面只保留一条受控路径：容器内 `epocha-ops admin`，目标必须 loopback。**
   应用既有的约束是"管理监听器绑 loopback、公共监听器没有管理路由"，本轮**没有**为了部署方便放宽它
   （不发布 8081、不做 SSH 隧道、不开任何未鉴权的恢复接口）。
   `ops admin` 自己钉三条：目标必须 loopback、路径必须 `/api/admin/*`、方法白名单。
   管理凭据是 Bearer 明文而管理监听器是明文 HTTP，放宽 loopback 约束需要的是 TLS + 明确的通道设计。
   容器内 loopback 与宿主 loopback 不互通这件事在 `DEPLOYMENT.md` §5 单独写一节——
   它是本轮最容易读错的一条。

   **演练撞出来的真实缺口**（因此多了一条命令，而不是多一个接口）：撤销掉最后一把管理凭据之后，
   `BootstrapAdminKey` 的"只在库里没有任何记录时登记"这个前提已经不再成立，换 `EPOCHA_ADMIN_KEY_FILE`
   完全不生效，而镜像里没有 `sqlite3` 可以手工改库 ⇒ 管理面永久锁死。第一轮演练正是在这里把自己关在门外。
   唯一受控出口是 `epocha-ops admin-recover`：**必须先停服**——命令自己探活，探到任何 HTTP 响应（含 401）
   就拒绝执行，因为"服务还在写账本时离线改 admin_keys"就是两份真相。它一条事务里做完
   撤销全部有效管理凭据 + 登记新凭据 + 写一条 `admin.recover_local` 审计；新凭据只写进 `--key-file`
   （`O_EXCL` + 0600，已存在即拒绝覆盖），stdout 只给 `key_id`。
   仍然**不做**未鉴权的恢复 HTTP 接口，也**不做**通用管理平台。
   运维纪律由它反推出来并写进 `DEPLOYMENT.md` §5：撤销管理凭据之前，先新增一把并验证可用。

6. **运行时镜像是 `FROM scratch` + 两把二进制，且构建期必须断言无 `PT_INTERP`。**
   交付面里"有 shell、有包管理器"不是运维能力，而是可执行任意命令的攻击面；没有 shell 就意味着
   `HEALTHCHECK` 不能用 `curl`，于是镜像里带一个只会打 `/readyz|/healthz` 的探针命令。
   **实测教训**：第一轮 `compose up` 直接失败，报 `exec /usr/local/bin/epocha: no such file or directory`——
   文件在镜像里，但宿主 `CGO_ENABLED=1`（有 gcc）产出的是**动态链接**二进制，scratch 里没有 `ld.so`。
   现在 `make docker-image-local` 强制 `CGO_ENABLED=0` 并用 `readelf` 断言无 PT_INTERP，
   把这类缺陷挡在构建期而不是等健康检查超时。
   镜像构建保留两条路径（容器内编译的规范配方 / `--build-context` 替换 toolchain 的装配路径），
   二者**运行时层完全相同**，由 `docker save` 的文件清单核对；这不是"两套部署方案"，
   而是同一份 Dockerfile 在构建机磁盘或 module proxy 不可用时的降级输入源。

7. **`cmd/loadtest` 的表述边界。** 它代算 PoW，只是为了把服务端三段 HTTP 的时延单独量出来；
   测的是**服务端吞吐形状**，不能用来推断访问者的解题体验（PoW 在浏览器里算）。
   并发与请求数都有硬上限（16 / 5000）：1GB 机器上无界压测会先把被测量对象打死，数据随之失真。
   它是开发期代码，`cmd/server` 不得链接（依赖隔离检查已把它加进禁链清单）。

### 未做（以及为什么）

- **在线热备份**：本轮只有"一致性快照 + 备份窗口内不做安全动作"这一条纪律。
  在线备份要处理的状态更多，而可证明性更差。
- **自动保留轮转**：工具不删任何历史文件。自动删除的代码分不清"我这轮生成的旧文件"与
  "别人放在这个目录里的东西"，误删的失败面不可逆。
- **恢复后的自动启用/批量启用**：逐个确认是流程的一部分，写成命令就变成"默认就全开"。
- **跨 schema 版本的恢复兼容**（旧快照在新程序上）与**多架构镜像**：都没有验证环境，
  写进 `BACKUP-RESTORE.md` §7 与 `DEPLOYMENT.md` §3 作为阻止安全开放的限制，而不是脚注。
- **管理后台页面、风险打分、自动淘汰、非视觉通道**：不属于本轮（阶段 5 的其余部分）。

### 影响

- 新增 `internal/store/deploy.go`（`Backup`/`VerifyBackup`/`Restore`/`Ready`/`PepperFingerprint`）、
  `internal/config/keyfile.go`、`GET /readyz`、`cmd/ops`、`cmd/loadtest`、
  `deploy/docker/{Dockerfile,compose.yml,.env.example,nginx.conf.example}`、根 `.dockerignore`、
  `docs/{DEPLOYMENT,BACKUP-RESTORE,STAGE5A}.md`、`make stage5a-check`。
- `store.DB` 多带一个 `path` 字段（只服务于写路径探测），`Config` 多带四个密钥**来源**标注（`env`/`file`/`none`）。
- DESIGN §6（密钥入口与 previous 密钥的恢复禁令）、§10.1（`/readyz`）、§12（备份方案与容器形状）、
  §15（`cmd/ops`、`cmd/loadtest`、`deploy/docker` 文件清单）、§17（阶段 5A 边界与验收）同步更正。
- 门禁退出码新增一层：`stage5a.sh` 用 **0=PASS / 1=FAIL / 3=BLOCKED**——
  部署与恢复演练没跑完时**不得**把"文件已编写"包装成"部署验收通过"。

## ADR-015 阶段 5B：运行互斥用 flock，不用端口探活；以及"可信"的四个维度

### 背景

阶段 5A 交付的 `epocha-ops admin-recover` 用一条 HTTP 探测来判断"服务是不是还在跑"，
并把 `--admin-base-url` 作为停服前置的检查手段。同一时期，`docs/STAGE5A.md` 的演练里
`/readyz=000000` 这类"探测失败"与"服务真的没起来"混在一起，说明我们把网络可达性当成了状态权威。
另一方面 DESIGN §12 与 `BACKUP-RESTORE.md` 里出现了"备份可信"这种说法，而实际提供的只有
sha256 与 `integrity_check`——那是完整性与一致性，不是来源真实性。

### 决策

1. **"能不能动这个数据目录"的权威判据是 `flock` 排他锁，不是端口探测。**
   实现 `internal/store/lock.go`：`<数据目录>/epocha.lock`，`O_RDWR|O_CREATE`（0600）+
   `LOCK_EX|LOCK_NB`。四条顺序与生命周期规则是这块机制的全部价值所在：
   - 服务在 `store.Open`（含迁移）**之前**取得，在 `db.Close` **之后**释放（defer 的注册顺序决定这一点；
     写反了会留下"锁已放、库还开着"的缝，那正是离线操作能挤进来的位置）；
   - **非阻塞**：拿不到就失败退出，绝不出现"运维以为在等、其实在死等"；
   - **永不删除锁文件**：崩溃/`SIGKILL`/容器被杀后内核释放锁，文件留在原地是正常状态。
     删锁文件会把两个进程分到两个 inode 上，`flock` 只认 inode，于是锁**静默失效**——
     这比没有锁更危险，因为它看起来像有；
   - **不是 PID 文件**：PID 会复用，"PID 不在就删锁"的窗口里两个写者可同时通过。
2. **只有"写这条数据目录"的动作需要这把锁。**
   `backup` 与 `verify` **不**取锁：在线一致性快照的正确语义就是允许与服务并发（只读连接 + `VACUUM INTO`）。
   给它们加锁会把备份变成"没人愿意按频率做的事"，而那是安全损失。
   `restore` 取 `--out-dir` 的锁：这既拦住"隔离恢复被写成就地恢复"这个最常见手滑，
   又不妨碍真正的隔离目录恢复（`stage5b.sh` 两个方向都测）。
   `admin-recover` 取 `--db` 所在目录的锁，`--admin-base-url` 这个 flag 被删除。
3. **能力边界必须写在文档里而不是脚注里**：`flock` 是建议锁，只约束按规矩办事的进程。
   同等文件权限下绕开本仓库代码直接打开 SQLite 的程序不受它阻止。本轮不引入强制隔离
   （独立属主、独占挂载、SELinux 之类），因此**不得**把它描述成防恶意本地进程。
4. **"可信"拆成四个独立维度，只声明真正提供的两个**：
   checksum（`manifest.sha256` + 体积，常数时间比较）与数据库一致性（`PRAGMA integrity_check` 只接受单个 `ok`
   + schema 版本闸门）是有过的；来源真实性（manifest 无签名）与保密性（快照是明文库）没有。
   因此"备份可信"的正确表述是：**备份目录的可写者 = 备份内容的作者**。
   要拿到来源真实性需要 manifest 签名 + 一把不进备份目录的签名密钥，那是设计题。
5. **运维身份规则由机制推出**：锁文件 0600 ⇒ 离线运维必须与数据目录属主同 uid。
   打不开锁文件报 `ErrLockAccess`，被占用报 `ErrLockHeld`——两族错误**必须分开**，
   因为处置方式相反（换身份 vs 先停服）；混成一句会让运维去等一个永远不会到来的释放。
6. **持续负载需要节流，而不是需要更大的并发。**
   `cmd/loadtest` 增加 `--pace`（每 worker 两次闭环之间的最小间隔）：
   没有它，450 次闭环会在 1 秒内打完，那样"5 分钟观察内存/WAL/题池随时间变化"根本无从谈起，
   而报告里若不打印 pace 与目标速率，峰值数字与稳态数字长得一模一样。
   抬高全局限流的实例**只用于测量**，不写进 compose——部署配置里不得混入测试高限流。

### 未做（以及为什么）

- 不做"锁等待/超时重试"选项：非阻塞拒绝 + 明确的"先停服"文案，比"看起来在等"更可诊断。
- 不做跨主机锁（NFS `flock` 语义不可靠，且本设计禁止把 SQLite 放网络存储）。
- 不做 manifest 签名：见第 4 条，它需要先解决签名密钥的存放位置，不能顺手加。
- 不"顺手"给 `backup` 也加锁：会被当作更保守的做法，实际上是把可运行的运维流程变成不可持续的。

### 影响

- 新增 `internal/store/lock.go`（+ `lock_test.go`）；`cmd/server/main.go` 的启动/关闭顺序改变（锁前置于迁移、后于关库）。
- `cmd/ops`：`admin-recover` 与 `restore` 取锁、`backup` 明确不取锁；`--admin-base-url` 移除；
  `probeStatus` 删除（无引用即不留）。
- 测试：`cmd/server`、`cmd/ops` 各有一组**真实子进程**测试（重新执行测试二进制按角色分派），
  覆盖抢同一数据目录、优雅重启、`SIGKILL` 后可重取、陈旧锁文件不阻塞、两进程抢恢复恰好一个成功、
  以及"在线备份不需要停服"这条反向断言。子进程按 pid 定向清理，绝不按名字模式批量 kill。
- `docs/DEPLOYMENT.md` 新增 §5.5；`docs/BACKUP-RESTORE.md` 的 §2 加入停服要求表与"四种可信"表、
  §5 加入"凭据文件与改库之间失败"的明确出口，§7 补三条不能保证项。
- 新增 `make stage5b-check` 与 `docs/scripts/stage5b.sh`；退出码沿用三态（0/1/3）。

## ADR-016 阶段 5B 附带修正：限流窗口比配置名松 60 倍（缺陷），以及"令牌桶"这个叫法

### 背景

阶段 5B 给门禁补"5 分钟持续演练"时，需要判断默认限流在低速率下会是什么形状。
顺着这条线读 `internal/risk/risk.go`，发现窗口分桶是 `bucket() = now().Unix()`（**每秒**一个桶），
而 `windowSize = time.Minute`、配置项叫 `EPOCHA_RATE_IP_RPM` / `rate_site_rpm`、`RetryAfter` 也按分钟报剩余时间。
两者不是一次"精度取舍"，而是差 60 倍。

**原表述**：DESIGN §9 与 §14-9、AGENTS 目录约定里把它叫"内存令牌桶"。实现从来不是令牌桶，
是**按 key 的固定窗口计数器**（`counter{bucket, count}`，`count <= rpm`）。

### 问题

1. `rpm=60` 的实际含义是"每个墙上秒允许 60 次" ≈ **3600 次/分钟**。红线 6 要求公开端点有**有界**限流，
   边界本身被静默放宽一个数量级；配置名、`RetryAfter` 表头、DESIGN 三处都声称是一分钟。
2. 为什么一直没被发现：唯一相关的测试 `TestLimiterBasicWindows` 把时钟一次推进整个 `windowSize`（60 秒）。
   60 秒当然也换了一个"秒桶"，于是它**同时**满足"窗口是一分钟"和"窗口是一秒"两种实现。
   跨秒但不跨窗口的中间态没有被测到——这是"测试推进的步长恰好掩盖缺陷"的典型形状。
3. 名称失准还有代价：读到"令牌桶"的人会假设它有连续补充速率与突发桶深两种可分开的参数，
   而固定窗口只有"窗口 + 配额"，边界处会有双倍突发（窗口交界两侧各打满配额）。

### 现在的立场

- 分桶改为**按窗口对齐**：`bucket = now().Unix() / int64(windowSize/time.Second)`；
  `RetryAfter` 用 `bucketStart(bucket)` 还原窗口起点（直接把序号当 Unix 秒会算到 1970 年附近）。
- 两条新测试把语义钉住：`TestLimiterWindowIsNotPerSecond`（推进 1 秒不得恢复配额，跨过整窗口才恢复）、
  `TestLimiterBucketBoundaryIsStable`（同一窗口内跨 30 秒仍算同一窗口）。
  原 `TestLimiterBasicWindows` 保留——它测的是"窗口滚动 + key 隔离"，两件事不重叠。
- 叫法统一改成"有界固定窗口计数器"（DESIGN §9、§14-9、§15、AGENTS）。
  本 ADR 保留"令牌桶"这个词出现在旧条目里的记录，不改写历史文本。
- **不做**的事：不把它改成真正的令牌桶（那是新的语义与新的可配置项，本轮没有需要它的场景），
  也不引入"滑动窗口"。窗口长度仍等于一分钟，因为它必须等于配置名声明的单位。
- 连带影响记录在 `docs/STAGE5B.md`：5A 的负载与"默认限流形状"数字是在旧窗口下量到的，
  修复后同样的压测形状会变（默认 60 RPM 真的变成约 1 次/秒），那些数字因此重新测一遍，
  而不是保留旧值再加一句注脚。

### 影响

- `internal/risk/risk.go`（`bucket()`、新增 `bucketStart()`、`RetryAfter`）、`internal/risk/risk_test.go`（两条新测试）。
- `api`/`admin` 里依赖限流计数的测试在修复后复跑（见 §门禁记录）；站点级 `rate_ip_rpm` / `rate_site_rpm`
  的语义从"每秒"回到"每分钟"，属于**收紧**，不新增任何放宽。
- DESIGN §9、§14-9、§15 与 AGENTS 的措辞修正。

## ADR-017 阶段 5B 收尾：第一版正式支持范围收窄为 B 路径；门禁结论按"三类归属"计算

### 背景

5B 主体交付后，`make stage5b-check` 给出的结论是"无失败但有 NOT_RUN ⇒ 退出码 3 ⇒ 不打完成标签"，
而那个 NOT_RUN 是 **A 路径（容器内编译）**：它需要 registry 可达与 ≥2GB 空闲磁盘，本机只有百 MB 量级余量，
且 Docker Hub 直连被黑洞（只有 mirror 可用）。当时的"唯一下一步"被写成了"去满足 A 路径的前提条件"。

同一轮还暴露了两处口径不成立：

1. 报告里同时写了"make stage5b-check 退出码 3"与"make 会把 3 折叠成 2"。实测（受控分支）：
   `make` 只能报 **0 或 2**，任何非 0 都被折叠成 2。所以"make rc=3"这句话是错的。
2. 上一轮的候选清单绑定的是 `stage-5a-done-dirty` 的工作树——那些 SHA-256 不属于任何干净提交，
   却被当成"部署候选"。

### 决策

1. **第一版只把 B 路径列为受支持且需要验收的构建路径**：宿主 `CGO_ENABLED=0` 静态编译 →
   `deploy/docker/.prebuilt/out` → named build context 装配运行镜像（`make docker-image-local`）。
   A 路径（`make docker-image`）**保持可选、NOT_RUN**。
   **这不是把 A 改成 PASS**，而是缩小正式支持范围：两条路径的运行时层完全相同（同一个 Dockerfile 的
   runtime 阶段），差别只在"二进制由谁编译"。
   代价一并写下：B 把工具链一致性交给执行者本机 Go（`GOTOOLCHAIN=local` 锁版本，但补丁版本可能不同），
   所以候选清单里 Go 版本那一行是**复现条件**。
2. **门禁结论按三类归属计算，只有必需项决定退出码**：
   - 必需（R）：受支持 B 路径的部署工程验收——互斥、恢复边界、真实进程测试、候选清单、
     **启动配方演练**、持续演练。FAIL ⇒ 1；BLOCKED/NOT_RUN ⇒ 3；全 PASS ⇒ 0。
   - 可选（O）：A 路径、amd64 交叉构建、root 场景下的 UID 65534。如实输出，**不决定退出码**。
   - 超范围（S）：产品效果项（人工可读性、抗 OCR/抗 AI、难度档）。只登记边界，永不打印 PASS。
   可选项在结构上不能被写成 PASS：`opt_pass` 必须携带"实际执行了什么"的证据字符串，缺证据直接 exit 2。
3. **给分类逻辑本身加负向测试**（`--selftest-classify`，9 条场景断言），并且用变异验证它有效：
   删掉 verdict 的 BLOCKED/NOT_RUN 规则 ⇒ 自测报 2 条 FAIL；把可选项计数并进必需项 ⇒ 报 4 条 FAIL。
   一个"永远通过"的分类自测与没有自测等价——这是本项目反复踩的同一类坑（§"判据本身写反"）。
4. **候选产物必须由干净提交构建**，清单落在忽略目录里（`deploy/docker/.prebuilt/candidate-manifest.txt`）
   作为**构建产物**，不提交进仓库：把"含当前 commit 的清单"提交进仓库会形成自引用循环
   （提交一改，清单里的 commit 就过期）。文档只指向固定的源码提交与标签。
5. **`stage-5b-done` 的覆盖范围写进标签正文**：仅覆盖 B 路径、`linux/arm64`、实际运行 UID/GID `1000:1000`；
   不代表 A 路径、amd64、公网 TLS、人工可读性或抗 AI/抗 OCR 已通过。

### 为什么不选别的方案

- "为了让 A 变绿去拉 380MB 的 golang 镜像"：被本轮任务明确禁止，而且它会把"验收"变成"下载竞赛"。
- "保留旧的『任何 NOT_RUN ⇒ 退出 3』规则"：那会让"缩小支持范围"这个决定无法在门禁里表达——
  范围收窄与"某项失败了"是两件不同的事，混在一个数字里就都得靠人读文案区分。
- "把清单提交进仓库以保可审计性"：清单里的镜像 ID 与二进制 SHA 每次重建都变；可审计性来自
  **绑定的提交 + 可复现的构建命令**，不来自把易变数值塞进 git。
- "改 `make` 让它透传退出码"：做不到，折叠是 make 的行为。可行的修法只有"把真码打印出来 +
  要求调用方读脚本/RESULT 行"，配方就照这个改了。

### 连带修正（同类问题，一次记下）

- `Makefile` 的 `run:` 配方自 5A 起就是坏的：`run: build` 后面用 TAB 直接接了 `@mkdir ...`，
  make 把它读成 prerequisites，`make run` 报 `No rule to make target '@mkdir'`。已修正。
- `DEPLOYMENT` §4/§11 的启动配方自相矛盾（先 `cd deploy/docker`，又要求"make 在仓库根执行"），
  且 `> keys/master` 没有覆盖保护——重跑一次就把主密钥换掉，等价于撤销全部已签发 token。
  改成"整段从仓库根执行、`-f/--project-directory/--env-file`、`set -C` + `[[ -e ]] ||` 幂等"，
  并由门禁第 2.5 步在隔离部署根里真跑一遍（七条判据，含"重建容器后已消费 token 仍被拒"）。
- 变量名双向对账最初写成"两个 grep 的结果都没有 ⇒ 无漂移 ⇒ PASS"：文件路径错的时候会**恒真**。
  现在取不到列表就是 FAIL，PASS 文案带上条数。

## ADR-018 阶段 5B 之后：清理凭据文件的判据必须是数据库事实，不是 error 的有无

### 触发

按"定点核实 admin-recover 的提交/清理边界"的要求读完**完整**函数后，确认存在一个真实缺陷：

```go
ak, revoked, err := d.RecoverAdminKey(...)
cerr := d.Close()
if err != nil { return err }
if cerr != nil { return fmt.Errorf("库已更新但关闭失败（请以 verify 复核后再决定是否重来）: %w", cerr) }
written = true          // ← 保留判定在这里，已经在 cerr 分支之后
```

凭据文件写好后由 `defer` 决定去留，而"该不该留"的开关 `written` 设在**关闭错误返回之后**。
于是"`tx.Commit()` 成功、随后句柄关闭失败"这条路径上：库里已经采用新凭据，
唯一副本文件被删，命令还提示运维"决定是否重来"。恢复动作自己制造了永久锁死。
另外 `f.Close()` 已经被显式调用过，defer 里再关一次只拿到 EBADF——错误被忽略不等于清理是对的。

### 决策

1. **恢复结果分阶段，不用 nil/non-nil error 代替事实**。
   `store.RecoverReport{Committed, Adopted, VerifyErr, Err}` + `KeepCredentialFile()`：
   调用方只问一个问题——"有没有理由相信库里已经（或可能已经）采用这把凭据"。
2. **提交结果不确定时用只读核查把它变成事实**。`tx.Commit()` 返回错误不等于库里没有这次写入。
   `store.AdminKeyAdopted()` 另开一条 `mode=ro` 连接读 `admin_keys`，因为服务/运维句柄是
   `SetMaxOpenConns(1)` 的**同一条连接**——未提交的行在它自己眼里是可见的，
   用它会得出"已采用"的假结论。这条理由有测试钉住（先证明事务内看得见，再证明只读核查看不见）。
3. **只有确认未采用才删文件**。可确认的清理路径是"key_id 生成之前失败"和
   "提交前的写入失败且只读核查确认库里没有这条"。
   未知方向时保留是可逆的选择：文件多余可以删，凭据丢了补不回来。
4. **收尾错误不冒充事务失败**。提交已确认之后 `Close()` 失败是一条警告，
   文案必须写"凭据已生效、文件已保留、不需要重跑"；退出码保持 0——
   把成功说成失败会诱导运维重跑，而重跑会再撤销一次并换成另一把。
5. **不新增未鉴权的恢复接口，也不为此重写 store 层**。`cmd/ops` 用三个包级函数变量做测试缝
   （open / recover / close）；生产路径取真实实现。测试注入的形状是"提交已确认但收尾失败"与
   "提交报错而库里已采用"——这两种在真实 SQLite 上按需构造不出来，而它们正是删除/保留的分界。

### 不做什么

- **不编造驱动能力**：没有伪造"COMMIT 失败但已落盘"的驱动钩子。store 侧用真实可构造的失败
  （拿掉 `audit` 表让事务内 INSERT 失败）验证"确认未采用 ⇒ 允许清理"；
  不确定形状只在 ops 侧注入。
- **不覆盖用户已有凭据文件**：`O_EXCL` 保留，拒绝覆盖的行为与测试都不变。
- **不动运行锁策略**，也不把"单实例"改写成"多实例支持"（见下面的第 4 条文档修正）。

### 连带修正的四处文档口径

1. **版本串与哈希**：`app_version` 来自构建时 `git describe`，而 `stage-5b-done` 在那次构建之后才存在。
   候选显示 `stage-5a-done-5-g993a792` 是正常的，**不为此重建候选**——重建会改变二进制与镜像 ID，
   记录就不再对应跑过验收的产物。只有运行时代码变化才需要新候选，且必须连验收一起重跑。
2. **三种材料丢失是三件事**（BACKUP-RESTORE 新增 §5.5）：`admin-recover` 只处理管理凭据丢失；
   master 丢了是已签发 token 失效（无法"找回"，只能重新签发），pepper 丢了是所有摘要对不上
   （只能重签发或用配对备份）。配好"库快照 + pepper + 当时的 master + 异机副本"才叫可恢复。
3. **健康检查 ≠ 重启**（DEPLOYMENT 新增 §8.5）：plain Docker/Compose 里 `unhealthy` 本身不会重启容器，
   进程退出才由 `restart: unless-stopped` 处理。不引入 autoheal，也不拿健康检查无条件 kill 服务；
   unhealthy 的正确动作是排查 + 告警。
4. **"SQLite 多进程会破坏一次性消费"这个绝对表述是错的**：一次性保证来自同一条 SQL 内的原子条件更新
   + `RowsAffected == 1`（ADR-004），跨句柄同样成立。本项目只支持**单实例**是实现与运维边界
   （数据目录上的运行锁 + 单一权威），不是数据库能力结论。本轮不开放多实例、不改锁策略。
