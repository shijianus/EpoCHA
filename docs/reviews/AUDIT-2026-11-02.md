## 3. 已确认、应优先修复的问题

以下问题建议定为 P2：应在继续试部署或扩展功能前修复，但本轮没有证据把它们描述为未鉴权远程接管。修复顺序以凭据生命周期、widget 生命周期、部署配方为先。

### 3.1 立即轮换未撤销仍在过渡期的旧站点凭据

- 位置：`internal/store/secrets.go:231-252`；管理 API 入口：`internal/admin/handlers.go:492-512`。
- 根因：`RotateSecret` 跳过所有 `RevokedAt != 0` 的凭据，而未来的撤销时间表示“过渡期内仍有效”，不等于已经失效。
- 触发：先用非零 `transition_sec` 轮换，让旧 secret 进入过渡期；在过渡期结束前再用 `transition_sec=0` 做立即轮换。
- 影响：前一轮旧 secret 仍能通过验证，直到原过渡期结束；“立即撤销旧密钥”的管理操作没有达到其声明效果。需要有权限的管理员操作触发，不是未鉴权的撤销绕过。
- 证据：从实际源码提取的 SQL/分支条件在内存 SQLite 探针中验证：第一次轮换 A→B 后，立即轮换 B→C，最后仍有效的是 A 和 C，而不是只有 C。未运行 Go HTTP 端到端复现；持有旧 secret 仍须提供有效 response，不能仅凭 secret 绕过题目或 PoW。
- 覆盖缺口：`internal/store/stage2_test.go:165` 分别测试 grace 与另一站点的立即撤销；`internal/admin/admin_test.go:497` 测试“立即→grace”顺序，没有覆盖“grace→立即”。
- 建议：按当前时间区分已失效、仍有效的过渡期和未排期撤销凭据；立即轮换必须覆盖全部仍有效旧凭据。已有更早的撤销截止时间不得被意外延后。
- 回归断言：连续两次轮换（先 grace、后 immediate）后，两个历史凭据均拒绝，新凭据可用；补充时钟边界、事务提交失败与重启后校验。

### 3.2 重复撤销并指定过渡期，可使已经撤销的凭据重新有效

- 位置：`internal/store/secrets.go:219-221`（站点 secret）、`:430-431`（admin key）。
- 可达入口：`internal/admin/handlers.go:532-556`、`:607-631`；两者验证参数后直接传入 `now + transition_sec`，没有阻止已撤销凭据的截止时间后移。
- 根因：撤销 SQL 无条件覆盖 `revoked_at`，而验证查询将未来的 `revoked_at` 视作有效。
- 触发：先立即撤销某个凭据，随后使用另一把有效管理员凭据对同一 key 再次撤销并设置非零过渡期。
- 影响：已撤销的站点 secret 或 admin key 被重新接受；与“重复撤销幂等”和“撤销不回滚”的设计约束冲突。此操作本身需要有效管理权限。
- 证据：使用仓库迁移及实际 SQL 的内存 SQLite 探针，两个凭据类型的有效匹配行数均从 `0` 变为 `1`。
- 建议：撤销截止时间只能保持或提前，不能通过重复 revoke 延后；已经失效的凭据应维持终态。将状态条件放入原子 SQL/事务中，不用事务外的读后判断替代。
- 回归断言：立即撤销后重复 revoke（grace 为 0 或正值）仍不可认证；原 grace 截止时间不能被延长；同时覆盖 site/admin、并发及重启。

### 3.3 widget reset 后，旧兑换响应仍可填回 token 并触发成功事件

- 位置：`web/widget/v1.js:1057`（reset）；`:995`（旧响应检查及后续成功写入）。
- 根因：reset 清理状态却没有递增异步世代 `gen`，旧请求返回时仍通过世代检查。
- 触发：组件已进入 `submitting` 时调用 `EpoCHA.reset(id)`，之后原 `/api/redeem` 返回成功。
- 影响：已放弃的验证重新呈现为成功，隐藏字段重新出现旧 token，宿主业务收到过时的 `onSuccess`。这不是服务端签名或一次性消费被绕过，而是前端生命周期错误。
- 隔离实测：reset 后状态先变为 `idle`，释放旧响应后变为 `verified`，隐藏字段恢复探针 token，`onSuccess` 调用次数为 1。
- 建议：reset 首先使当前世代失效，再取消请求、worker、过期计时和排队重试；所有异步回调统一核对世代。原生表单 reset 应遵循同一契约。
- 回归断言：reset 后即使旧兑换成功返回，状态仍为 `idle`，`getResponse(id)` 与隐藏字段为空，成功回调不增加。
- 覆盖缺口：`docs/scripts/browser/widget_browser.test.mjs:406,478,755` 覆盖其他状态的 reset，但未覆盖兑换在途时 reset。

### 3.4 widget 兑换请求没有超时，网络挂起时界面无法自行恢复

- 位置：`web/widget/v1.js:980,992`。
- 根因：redeem 的 fetch 未使用 AbortSignal/超时计时器；进入此阶段时原题目期限计时器也已清理。
- 触发：PoW 完成后，`/api/redeem` 请求一直不返回。
- 影响：`fetchTimeoutMs` 不约束兑换，组件持续停在 `submitting`，输入、提交及换题按钮不可用。
- 隔离实测：设置 `fetchTimeoutMs=1000`，虚拟时间推进 60 秒后仍为 `submitting`；请求 `signal` 为 `undefined`，没有兑换超时计时器，换题按钮仍禁用。
- 建议：兑换增加有界超时和 AbortController，结束时清理，并与 reset/destroy 的世代失效协同。超时不能把验证视为成功；服务端是否已经消费可能未知，应允许获取新 challenge，而不是静默重复兑换。
- 回归断言：超过超时后进入受控错误态、token 为空、允许换题；晚到成功响应不能覆盖重试后的状态。
- 覆盖缺口：`docs/scripts/browser/widget_browser.test.mjs:426` 仅覆盖 PoW 计算超时，不覆盖兑换 HTTP 挂起。

### 3.5 试部署命令会检出缺少后续恢复修复的旧标签

### 3.6 备用密钥生成配方创建 root 专有文件，非 root 服务无法读取

- 位置：`docs/DEPLOYMENT.md:34-42`（§2）。
- 根因：`sudo tee` 创建 root-owned 密钥文件，并设置为 `0600`，却没有同步服务运行身份的文件属主。
- 影响：按此配方准备文件，再以非 root UID 运行服务时，服务不能读取启动必需的密钥。
- 范围：这是 §2 配方的问题；§11 按同 UID 创建文件的主配方不受此问题影响。
- 建议：统一密钥准备用户与服务 UID/GID，保持 `0600`；不能通过放宽为全局可读绕过。补充非 root 挂载读取与重跑不覆盖密钥的验收。
- 本轮为权限语义与配方的静态确认，没有在本机修改权限或提权运行。

## 4. 次级工程观察与加固建议

这些观察不计入上述六项主要问题，也不应在没有对应验证时包装成漏洞结论。

### 4.1 Windows 检出会破坏文本字节保真检查

当前 Git 系统配置为 `core.autocrlf=true`，仓库没有固定 LF 的 `.gitattributes`。`git ls-files --eol` 显示受测 Go/Shell/Makefile 为 `i/lf w/crlf`。

- 原样 Node 测试的 worker 副本断言只去掉末尾 `\n`，残留 `\r`，因此出现一项真实测试失败。
- 将被测文本仅在内存中统一 LF 后，同一套 7 项测试全通过；这不是修复已经落地，也不是 PoW 算法失败。
- 原样 gofmt 会列出 81 个文件；对 Git 提交原始 LF 字节逐一运行 gofmt，81 个均无需格式化，不能将其误报成 81 个源码格式问题。
- 建议通过仓库级 `.gitattributes` 为 Go、JS、Shell、Makefile 等固定 LF，保留二进制资产的正确属性，并新增 Windows checkout 检查。不要为了通过测试改用户全局 Git 设置。

### 4.2 就绪检查并不充分证明磁盘数据写入成功

`internal/store/deploy.go:131-149` 的探针打开主库并创建零字节临时文件，但没有实际 Write/Sync。它可以检查部分权限/目录可写条件，不能据此保证所有 ENOSPC/WAL 追加故障都可被识别。

建议收紧文档承诺，并在受控环境验证“还能创建目录项但数据写入失败”等情形；若补强探针，应保持有界、无业务 token 消费的语义。本轮未制造满盘或注入文件系统故障，因此该项是**条件性加固观察，ENOSPC 未复现**。

### 4.3 管理失败限流发生在实际鉴权之后

`internal/admin/admin.go:198,215` 先执行凭据匹配，再对失败响应限流。429 不代表已经避免数据库鉴权扫描成本。正确凭据不受失败锁定影响也可能是防止锁死管理员的设计，不能据此声称认证绕过。

管理面默认 loopback，影响范围较小。建议明确区分失败响应策略与成本限流，在保持合法运维可恢复的前提下补充成本边界测试。

### 4.4 有效 secret 上限的计数口径需要统一

`internal/store/sites.go:28` 将上限描述为“同时有效、含过渡期新旧并存”；`internal/store/secrets.go:120` 的新增计数却只统计 `revoked_at IS NULL`。未来撤销时间对应的 grace 凭据仍可有效，但不计入此口径。

建议在修复 3.1/3.2 时共同定义“有效凭据”，验证重复轮换和新增组合是否遵守同一上限，避免多个函数各自解释生命周期。

### 4.5 历史验收记录不能替代当前提交的自动门禁

仓库有较丰富的 Go、Node、浏览器和阶段脚本，但本次没有发现入库的 CI 配置或版本化提交 hooks；这不等于确认远端没有外部 CI。

建议先建设与正式支持范围一致的 Linux 门禁：固定允许的 Go 工具链，格式检查、vet、`go test -race -count=1 ./...`、JS 共享向量、真实浏览器竞态测试、受支持 B 路径的部署与恢复。运行时纯 Go/CGO_ENABLED=0 与测试时为 race 提供 C 工具链是两件不同的事。

`docs/STAGE5B.md:291` 记录修复后候选 `be95275` 仍有一项必需持续演练 BLOCKED；不能因为它包含修复就省去重新验收。历史清单是构建收据，不是字节级可重复构建配方（同文件 `:315`）。

### 4.6 README、离线归档与完成状态存在漂移

- README 同时保留“没有离线 OCR/未测”的历史表述和后面的实测 96%/31%/3% 结果，应明确标历史阶段，避免读者误判当前状态。
- README 所称旧 `epocha-offline-assets.tar.gz` 会在启动时自动装载，没有相应代码/构建引用支持。生产生成器的嵌入资产不依赖这份开发评测归档。
- 该约 20.6 MB 归档包含开发评测资产与开发二进制；`.dockerignore` 未排除它，会扩大可选 A 路径的构建上下文/构建缓存。**不能据此推断最终运行镜像包含它，更不能声称 HTTP 泄露了答案。** B 路径只装配指定二进制。
- 建议区分生产必需资产、可再生评测输出和离线备份；在明确引用关系后制定归档保留方案，不直接删除现有文件。

## 6. 建议的后续开发顺序与完成标准

### 第一批：可靠性修复，不扩功能面

1. 先补凭据撤销/连续轮换回归测试，再修复 3.1/3.2，并统一有效凭据上限口径。
2. 先补 reset 在途、兑换超时、晚到响应与重试隔离用例，再修复 3.3/3.4；保持后端一次性验证与 fail-closed 语义。
3. 修正文档候选 OID、密钥 UID/GID 配方及陈旧状态；不移动已发布历史标签。
4. 固定仓库文本换行，提供可复验的开发环境与自动门禁。

完成标准：新增测试确实先失败后通过；完整 Go race 回归、现有阶段回归、真实浏览器交互以及受支持部署/恢复演练有当次证据。没有这些证据不打新的完成标签。

### 第二批：管理控制台 M2 与可观测性

基于已有管理 API 补题池观测、审计日志、凭据轮换/撤销视图；仍只挂在管理监听器。先交付真实计数、明确窗口和错误分族，不编造成功率/QPS 图表，也不记录 secret、token 或答案。

完成标准：页面对接真实数据，分页与错误态齐全；凭据仅一次性展示，刷新、离开、401 后清理；轮换/撤销流程与第一批修复后的契约一致，并有真实浏览器验证。

### 第三批：验证效果与可访问性，再考虑风险打分

- `arithmetic-baseline-v1` 仅是工程基线，不能作为抗自动化题型。
- 仓库记录的离线 OCR 低/中/高档通过率为 96%/31%/3%，是**历史特定工具与样本结果，本轮未重测**，不能外推为抗现代 AI 的结论。
- 保持图片题 `experimental:true`、`production_ready:false`；补充真实人工可读性/耗时/失败率和非视觉等价通道，低档 OCR 弱点不能靠宣传规避。
- 先定义并采集不含敏感内容的观测指标，再做风险评分/多生成器权重。自动降权应遵守多信号与人工确认的既有约束，不能仅凭通过率判定机器破解。

完成标准：工程正确性、人工可用性、机器评测分别给证据与边界，不能互相替代；风险模型没有样本验证时不得改变为静默放行。

### 暂不扩大支持范围

优先保留单节点 SQLite、运行锁和现有管理网络边界。正式部署验收范围仍按 ADR-017 的 B 路径、linux/arm64 及历史实测 UID/GID `1000:1000` 声明；默认 `65534:65534` 历史验收受阻，默认配置不等于已经验证。本轮没有把 Windows、amd64、A 路径、公网 TLS 或其他未测环境升级为正式支持。Windows 原生运行另有 Unix `syscall.Flock` 边界（`internal/store/lock.go:113`），不应仅升级 Go 就宣称可以原生运行。Cloudflare 边缘、多实例、分布式存储和更多依赖应排在上述可靠性与效果验证之后。

## 7. 审计判断

本轮未发现足以确认未鉴权伪造 token、跨站 secret 消费合法 token、或直接绕过一次性状态消费的证据；检查到的域分隔、恒时比较、条件状态更新、提交后成功、来源边界等仍需完整回归维持，有限审计不为未覆盖路径背书。

当前最值得推进的不是重写架构，而是让“撤销就是撤销、reset 就是 reset、挂起可以恢复、文档部署到正确版本”成为可重复验证的事实。本报告提供了修复落点与完成标准；本轮没有应用这些业务修复，也没有把现状标记为生产就绪。
