仍需 §B-01 的 full 门禁；若要对公网提供服务，再单独做域名/TLS/反代/防火墙授权与验收。

### B-03 · P1 · `synchronous=NORMAL` 的掉电持久化缺口仍是上线阻断

**事实**：`internal/store/store.go:83` 的 DSN 固定
`_pragma=synchronous(NORMAL)`；`docs/DECISIONS.md:974` 明确写着：
“本轮不修改 ADR-007 的 `synchronous=NORMAL`。FULL 变更需单独明确持久化与性能取舍并确认；
其掉电保证缺口保持上线阻断。”

**影响**：进程崩溃与正常重启有 WAL 保护，但**掉电/OS 崩溃时最近事务可能丢失**。
对验证服务而言，丢失的可能是已经提交的 response 消费、撤销或审计记录；这类丢失的方向
不是“安全收紧”，而可能是“已消费 token 又能被接受”。这不是本轮引入的缺陷，但它仍然是
上线前必须显式决策的持久化边界。

**建议**：不要在本轮静默改成 `FULL`。先由用户/维护者决定：
1. 生产上线前改 `FULL`，并测量 1 vCPU/1GB 上的写入时延与吞吐影响；或
2. 明确接受 `NORMAL` 的掉电窗口，写进 ADR/运维合同，并在 VPS 试部署中标注“不是生产持久化认证”。

无论选哪条，都不能把“进程重启后不可重放”写成“掉电后也不可重放”。

### B-04 · P1 · 人工与效果验收仍未完成

- `text-image-v1` 仍是 `experimental:true` / `production_ready:false`；
- 历史 OCR 低/中/高档 96%/31%/3% 是单一工具、固定配置的严格整串通过率，不是当前 M4，
  也不是抗现代 AI 的认证；
- 人工可读性、辅助技术、真机移动端、题型人工各过 5 次均未执行；
- 管理台的 403/5xx 文案、剪贴板、真机移动端、辅助技术仍是 `NOT_RUN`；
- 远端 Chromium 已完成一次**功能**浏览器闭环（图片题 verified → 留言 #1 → 重放拒绝），

## 6. 代码与运维修正项

### F-01 · P1 · 停用/撤销与消费的原子性只覆盖 response，不覆盖站点状态

**证据**：

- `internal/api/handlers.go:598` 在 handler 里检查
  `!site.Enabled || site.Version != claims.Svid`；
- `internal/api/handlers.go:606` 随后才调用 `ConsumeResponse`；
- `internal/store/store.go:515-525` 的 `ConsumeResponse` 事务只检查
  `responses.used=0` / `expires_at>now`，**不检查站点 enabled/version，也不检查 secret 是否已被撤销**；
- `internal/api/stage2_test.go:487-530` 的并发测试只断言“最多成功 1 次”，并明确把
  “成功 0 或 1”都称为已定义结果；`internal/store/stage2_test.go:310-317` 甚至在停用后
  调用 `ConsumeResponse` 时只 `t.Logf`，不把它判失败。

**本次 VPS 顺序测试**：取一个未消费 response → 停用站点 → `/siteverify` 失败；
重新启用（version 2→3）→ 同一 response 仍失败。顺序语义是对的，但这不证明并发窗口已闭合：
handler 的站点检查与 `ConsumeResponse` 仍是两个事务，现有并发测试也不要求“停用先提交 ⇒ 消费必失败”。

**影响**：一个 `/siteverify` 请求如果在停用提交之前读到了 `site.Enabled=true`，在停用提交之后
才执行消费，仍可能成功。类似地，`/api/redeem` 的站点状态检查也在 `RedeemAttempt` 事务之外。
这使“停用后未消费 token 立即失效”“撤销后不消费合法 response”的**绝对表述**不成立。
窗口很窄，且需要请求已经在途；但停用通常正是为了立刻止血，语义不能靠“通常很快”保证。

**建议（二选一，不要含糊）**：

1. **收紧实现**：把 `sites.enabled` 与 `sites.version` 纳入 `ConsumeResponse` 的同一事务
   （例如在 UPDATE 里加 `EXISTS (SELECT 1 FROM sites s WHERE s.id=responses.site_id AND s.enabled=1 AND s.version=?)`），
   并在 `RedeemAttempt` 里对 `site_id` 做同样校验；补一个确定性交错测试：
   先读站点 → 停用提交 → 再消费，必须失败。
2. **明确放宽语义**：在 DESIGN/ADR 里把“立即失效”改为“停用与在途消费按提交顺序竞争，
   在途请求可成功一次”，并让测试真正覆盖“停用先提交 ⇒ 消费失败”这一方向，
   而不是只允许 0 或 1。

当前代码和测试的表述比实现更强，不能同时保留两种说法。

### F-02 · P2 · `MaxSites` 的硬上限在事务外计数，可被并发建站突破

**证据**：`internal/store/sites.go:200` 在 `BeginTx`（221 行）之前
`SELECT count(*) FROM sites`；真正的 `INSERT INTO sites` 在 233 行。两个并发管理请求可以
都读到 511，然后先后提交，最终超过 `MaxSites=512`。

**影响**：`MaxSites` 是 `FindSiteBySecret` 全表扫描上界的一部分；突破上限不会直接泄露数据，
但会让“有界扫描”这一资源不变量失效。管理面是可信面，风险低于公开面，但仍是可修复的竞态。

**建议**：把计数与插入合并为一条条件 INSERT（类似 `insertSecret` 的写法），或在一个
先取得写锁的事务里完成；补两个独立 DB 句柄并发建站的测试，断言最终行数不超过 512。
不要在 `*sql.Tx` 上再执行 `BEGIN IMMEDIATE`（红线 3）。

### F-03 · P2 · 备份/恢复“已发布但持久化未确认”仍以退出码 0 结束

**证据**：`internal/store/deploy.go:354-367` 的 `publishBackup` 在数据库与 manifest 都已发布、
但 `syncDirectory` 失败时返回的是 `warning`，不是错误；`cmd/ops/main.go:157-158` 只打印警告并
返回 nil。`Restore` 的 `rep.Warning` 同样只打印（`cmd/ops/main.go:247-248`），进程退出码仍为 0。

**影响**：人工看 stdout 能看到警告；但 cron/自动化只看退出码时，会把“目录同步失败、
持久化尚未确认”当成成功备份。对一个用来防重放的账本，这会把“文件存在”误读成“备份可信”。

**建议**：为“已发布但持久化未确认”定义独立退出码或 `--strict` 行为，至少在自动化配方里
把警告升级为失败；保留“已发布文件不删除”的安全方向，不要用清理动作回滚已经交付的路径。
把“备份已发布”和“备份已持久化确认”分开写进 BACKUP-RESTORE。

### F-04 · P2 · 本机工作树的忽略目录会污染 Go 包清单与发布门禁

**证据**：当前工作树 `full` 的唯一 FAIL 是
`go-package-inventory`，列出
`release-artifacts/c04-c08-…/red-audit.go`、`red-secrets.go`、`windows-lock.go`、
`convergence-development-…/auth/windows-lock.go`、`tmp/gui-harness/main.go`。
这些文件被 `.gitignore` 忽略，但 Go 的 `./...` 不读 `.gitignore`，因此会进入 `go list`/`go vet`/`go test`。

**影响**：同一份源码在不同工作树会得到不同的门禁结果；本机 `make check` 可能因为历史证据目录
而失败，开发者会误以为是代码问题。干净 worktree 的 `full` 是 `INCOMPLETE/3`，没有这个 FAIL，
正好证明污染来源。

**建议**：正式验收固定使用干净 worktree/隔离源码快照；本机工作树不作为候选。
如要长期改善，可把历史 `.go` 证据移出仓库目录，或在门禁中明确以 Git 清单为准；
不要为了让 `./...` 通过而删除用户的历史证据文件。

### F-05 · P3 · 所有管理凭据都被撤销时，启动日志没有“无可用凭据”的告警

**证据**：`cmd/server/main.go:306` 只在 `len(keys)==0` 时打印
“库中没有可用管理凭据”；`ListAdminKeys` 返回的是全部行（包括已撤销行）。
如果最后一把管理凭据被撤销，`len(keys)>0`，启动时不会出现这条告警，但管理 API 实际全部 401。

**影响**：运维在锁死时缺少最直接的启动提示；只能从 401 反推。安全性不受影响（拒绝方向正确），
但可运维性变差。

**建议**：统计“当前仍有效”的 admin key 数量，为零时告警；不要因此自动 bootstrap 或复活旧凭据。
告警文案应指向 `epocha-ops admin-recover`。

### F-07 · P3 · 管理监听器非 loopback 时只告警，不拒绝启动

**证据**：`cmd/server/main.go:310` 对非 loopback 的管理监听地址只打印

### F-09 · P2 · 反代后 exampleapp 的 sameSite 只看 Host，公网表单会被拒

**事实**：`cmd/exampleapp/main.go:568-600` 的 `sameSite` 在存在 `Origin` 时比较
`url.Parse(Origin).Host == r.Host`；instabox 的公网代理把上游 `Host` 变成
`127.0.0.1:18091`，于是公网页面 `Origin: https://18094-…`（以及上一轮的 `18092-…`）的表单 POST 被

**影响**：任何把 exampleapp（或其他业务后端）放在改 Host 的反代后、又只比较 `Host` 的接入，
都会在真实浏览器里失败。这不是生产验证服务的缺陷，但会让“接入示例”在反代形状下不可用，
容易被误判成 CAPTCHA 验证失败。

**建议**：生产业务后端应明确配置反代保留 `Host`，或只信任受控的 `X-Forwarded-Host` 并限制来源；
不要把测试代理当生产配方。把该形状写进接入文档/验收：公网页面 Origin、反代 Host、业务后端
允许来源三者必须一致。

### 7.1.1 压力与题池结果

**判定口径**：这里的“失败”只按 HTTP/业务结果计数；`503 challenge-unavailable` 是设计中的
可重试容量信号，不是静默降级。测试实例用了**测试专用**的高限流（全局/站点 100000），
生产默认仍是全局 IP 60 RPM、站点 60/300；不要把本表当成“生产默认配置下 300 并发可用”。
首轮未提高全局限流时，300 个请求有 278 个 429；这验证的是默认全局限流先于题池生效，
之后才用测试限流单独测题池容量。

| 场景 | 结果 | 读法 |
|---|---|---|
| 算术完整闭环，瞬时 300/并发 8 | **150 成功 / 150 503**；150 个成功闭环全部 redeem+siteverify 200；重放检查 6 次、拒绝 12 次；p95 总时延 189ms | 题池高水位 100，瞬时 300 超过供给；503 是明确容量信号 |
