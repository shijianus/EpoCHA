# EpoCHA 上线收敛审计与完整修复建议（2026-11-02）

## 1. 审计结论

**当前工作树不满足正式上线条件，也不能把现有发布入口的结果直接当成可信的发布认证。** 本次确认了管理凭据恢复遗漏、一次性凭据交付、恢复产物落位等安全与恢复边界缺陷；同时发现发布门禁必失败、负测因错误原因通过、候选清单不能忠实描述实际构建输入的问题。

工程基础值得保留：HMAC 域分隔、常数时间比较、SQLite 原子条件消费、站点与来源绑定、独立管理监听器、有界限流与题池、纯 Go 静态交付都有明确实现与测试。需要修复这些基础之上的边界，不需要重写架构或引入新的数据库、框架、运行时依赖。

还必须区分两个目标：

- **受限试部署**：在明确授权的目标机，以 B 路径 / Linux arm64 / 已验证服务身份运行，验证现有工程功能、恢复流程与实际接入。修复本报告的阻断项后，才有条件做该验收。
- **按原需求的完整产品上线**：还需完成风险打分、题型权重与选择、统计及分级淘汰、非视觉等价通道、完整管理流程等既定能力。不能通过把它们永久排除在发布门禁之外，宣称原需求已经完成。

目前两个题型仍为 `experimental:true / production_ready:false`。历史 OCR 的低/中/高档 96% / 31% / 3% 是单一工具与固定配置的严格整串通过率；它不是抗现代 AI 的认证。人工可读性、非视觉通道、真机与辅助技术仍缺验收。**容器能启动、Go 能编译和人机区分能力是不同的验收结论。**

本轮交付是审计报告及建议，未修复业务代码，未部署，未安装依赖，未提交、推送或打标签。

## 4. 上线前必须修复的事项

### F01 · P1 · admin-recover 漏撤销仍在过渡期的管理凭据

**证据**：`internal/store/deploy.go:788` 只更新 `revoked_at IS NULL`；真实鉴权 `internal/store/secrets.go:504` 接受 `revoked_at IS NULL OR revoked_at > now`。

**触发与影响**：旧管理凭据先被设置一小时过渡期，再停服执行 `admin-recover`。旧行的撤销截止时间非空，不被恢复操作更新；恢复后旧凭据在截止前仍可登录。恢复管理访问不能实现其承诺的“撤销全部仍有效管理凭据”，对疑似旧凭据泄露后的处置尤其重要。

**最小复现**：直接提取当前 RecoverAdminKey 的原始 UPDATE，在内存 SQLite 中插入正常有效、未来撤销、已过期三种记录。执行后，未来撤销的旧 key 仍被真实有效性 WHERE 条件选中。没有使用任何真实凭据。

**修复建议**：同一恢复事务内，将所有 NULL 或未来截止时间统一收紧到本次 now；保留更早已失效的截止时间。新凭据、撤销、恢复审计继续同事务提交，保持现有凭据文件保留与只读核查纪律。

**验收**：覆盖 NULL、多个未来截止时间、恰好 now、过去时间；重启后所有旧凭据均拒绝、新凭据成功；插入或审计失败时整个恢复事务回滚，唯一凭据文件的处理仍依据数据库是否采用。

### F02 · P1 · 管理写入与审计分离，可能丢失唯一一次的新凭据交付

**证据**：`internal/admin/handlers.go:275` 创建站点后，284 行另写 Origin，291 行再审计；477/483 行新增 secret 后审计；512/518 行轮换后审计；589/595 行新增管理 key 后审计。失败时在返回一次性明文之前退出。

**触发与影响**：

- 创建站点附带非法 Origin，可以返回 400，但站点和首把 secret 已创建，明文没有交付；这是无需制造存储故障的可达分支。
- 新凭据已提交，之后审计写入失败，返回 500，库里留下调用方不知道的有效凭据。
- 立即轮换 `transition_sec=0` 时，旧 secret 已撤销，新 secret 的唯一明文却未返回。业务失去已知可用的验证凭据，需要管理员再次处置；不应描述为永久失去全部管理能力。

**修复建议**：创建站点、Origin、首把 secret 和相应审计应作为一个业务事务；新增凭据与轮换的审计也应纳入其提交边界。先更新 DESIGN/DECISIONS 对该边界的说明。`internal/admin/admin.go:266` 当前说明撤销/停用失败后不回滚，是安全收紧方向的选择；**不能因此把所有管理动作一概改成审计失败就恢复旧权限**。区分“生成与交付新凭据”和“紧急撤销/停用”两类动作，写清提交不确定时如何核对。

把审计纳入事务可以修掉本次内部失败窗口，但不能保证提交后网络一定交付成功。对新 secret 交付中断，还需提供明确的查询状态、重新签发和安全轮换操作说明；不得自动重放立即轮换。

**验收**：非法 Origin 不留下站点和 secret；通过数据库触发器或故障注入让审计失败，新增/轮换不能留下未知有效凭据或撤销旧凭据后丢掉新凭据；成功响应同时对应已提交变更与审计。紧急撤销的收紧语义另测。

### F03 · P1 · 恢复副本在完成保守失效前就使用最终文件名

**证据**：`internal/store/deploy.go:578` 复制原始快照到 partial，586 行先 rename 到最终 `.db`；591 行读计数，606 行才执行禁站点、清凭据与 token 等 transform。

**触发与影响**：rename 后进程崩溃，或 readCounts / sidecar 清理失败，最终名称可能保留尚未失效的旧快照。操作者如果误将该文件接入服务，可能重新接受快照中的旧管理或站点凭据。某些后续错误分支有清理，不能覆盖进程终止和较早返回路径。此项已由代码顺序确认，完整崩溃实验本轮未运行。

**修复建议**：在隔离的临时文件上完成迁移、保守失效、审计、关闭、完整性与计数核查、WAL 收尾，全部成功后才以原子且不覆盖既有目标的方式交付最终名称。临时中间物不能被运行配方识别成完成产物。继续持有输出目录运行锁。

**验收**：在复制、计数、迁移、transform、提交、完整性、收尾各处注入失败与进程终止；失败时不存在最终交付名称，或最终名称只能指向已经完整失效的库。不得覆盖已有库；工作库与原备份保持不变。

### F04 · P1 · 示例业务后端接受非 200 响应中的 success:true

**证据**：`cmd/exampleapp/main.go:560` 使用 `StatusCode != 200 && !got.Success`，最后返回 `got.Success`。

**触发与影响**：固定验证上游返回 `500 {"success":true}` 时，示例仍允许业务写入，违反“5xx 一律失败关闭”的接入示范。当前没有证明普通浏览器请求能使真实 EpoCHA 产生该响应；风险是异常上游响应被接受，以及错误范式被复制到生产业务。

**修复建议**：只有 HTTP 200、响应可解析且 `success:true` 同时成立才授权；其余结果均拒绝受保护操作。

**验收**：4xx、5xx 携带 success:true，超时、非 JSON、截断体、success:false，JSON 与原生表单两种路径都零新增；正确响应才写一次。

### F05 · P1 · 题池水位与真实可领取条件不一致，可造成持续 503

**证据**：`internal/store/pool.go:229` 的 ReadyCount 仅要求 `expires_at > now`；329/334 行的领取要求题目晚于 `challenge.ExpiresAt` 过期；`internal/pool/pool.go:402` 在 ready 足够时停止补题。

**最小复现**：用当前两段原始 SELECT，在内存 SQLite 放 24 道剩余寿命 120 秒的图片题，challenge TTL 为 180 秒。ReadyCount=24、可领取候选=0、低水位=8，worker 不补题。默认题目寿命为 4200 秒，低流量下整批老化也会到达该形状；最大 challenge TTL 为一小时，不能只考虑默认三分钟。

**修复建议**：按对应分桶启用站点的有效 challenge TTL 计算可服务水位，提前补题，并把管理面的“ready”与“能满足签发寿命的可领题”区分清楚。处理不可领的 ready 行时保持行数/图片预算上界，不重用 assigned 题，不将池空降级成 PoW-only。对题目 TTL 不足以支持站点 TTL 的配置给出可操作的拒绝或明确诊断，不能仅靠注释承诺警告。

**验收**：可控时钟覆盖低流量老化、同桶不同 TTL、修改站点 TTL、旧题接近到期、图片预算受限、worker 重启；整个周期存在可服务题，或明确返回容量错误且及时恢复，不能 ready 很高但长期全 503。

### F13 · P2 · 负载与资源门禁的成功判据过弱

`cmd/loadtest/main.go:73` 的契约是至少一次成功返回 0；`docs/scripts/stage5a.sh:1206` 主要据退出码判断资源演练，不能证明 150/150 成功。`stage5b.sh:990` 后图片站点及水位、采样只记录而缺强制非空/非零/可解析检查；450 次节流近似五分钟，不是严格总超时。

保留负载工具的通用语义，但验收脚本另断言请求计划、成功总数、每种失败、总时限、实际图片生成、采样完整性、OOM/重启。目标与实测必须同口径：容器内存不是 RSS，p50/p95/max 不是 p99，pow_only 流量加后台图片补池不是图片题完整吞吐。

至少补测：空闲超过题目 TTL、真实图片领题/作答/放弃、图片预算满载、多个分桶、默认限流下流量、备份并发、磁盘受限、长时间 DB/WAL 与 RSS。持续时长应覆盖题目 TTL 和清理周期；全天运行形状可用 24 小时观察，但时长本身不代替判据。

图片留存的正确边界：`internal/store/store.go:576` 分批删除 terminal 或已过期题，每轮最多 500 行，清理周期为一分钟。已完成/答错图片**不必等 4200 秒**；未终态 assigned 题会占用预算直到题目过期。不要据此错误推导“所有图片都留 70 分钟”，也不能保证有积压时下一轮一定释放全部 terminal 图片。

**弃答后的预算滞留是 P2 可用性设计缺口，不只是测量不足。** challenge 默认 180 秒后已不能兑换，但绑定图片的过期时间仍来自题目生成时的 4200 秒 TTL。`Purge` 不依据绑定 challenge 已过期来清除 assigned 图片；这些行仍被 `ImageAssetBytes` 与 INSERT 的全局字节预算计入。worker 在 `internal/pool/pool.go:389` 用“已用字节 + 65,536”做保守预检，剩余空间不足时停止该图片桶补题。已有可领取题耗尽后，依赖图片题的站点可能持续得到 503；预算是全局的，一个站点的弃答量也可能影响其他图片站点。实际滞留时间取决于被领题的剩余寿命、后续流量与清理批次，不能把每次影响固定写成 70 分钟。

**最小隔离复现**：提取当前 Purge 的三段原始 SQL，在启用外键的内存 SQLite 中分别插入 64 条 terminal 或 assigned 图片记录，每条合成资产 65,536 B、总量 4,194,304 B；在 challenge 已过期、图片尚未过期时执行清理。terminal 组图片预算降至 0；assigned 组仍保留全部 4 MiB，worker 的下一张预检失败，绑定 challenge 行也因外键引用条件继续保留。此实验验证清理与预算机制，**不是**生产 PNG 大小、网络压测或已成功实施的拒绝服务实验。

容量数字只能作估算：4 MiB / 单题 64 KiB = 64 条，是按单题上限计算的合成容量；按历史 d5 均值 6,315 B 并考虑 worker 保守预检，约 654 条图片记录就可能停止补题。这些记录还包括 ready、assigned、terminal 的混合占用，不能称为固定的请求触发次数。现有 IP/站点限流及活动 challenge 上限会限制积累速度，但活动上限只统计尚未过期的 challenge，不能释放其过期后仍占预算的 assigned 图片，因此不能替代该项修复。

**修复建议**：先明确并记录题目“可领取寿命”和“绑定后保留寿命”的区别。领取后依据库中 challenge 的权威到期时间，安全收紧已绑定资产的保留期限；或在清理事务中处理绑定 challenge 已过期/不可再成功兑换的 assigned 题。具体方案须先更新对应 DESIGN/ADR，并证明不删除仍有效作答所需 verifier、不削弱一次性消费、不让任何 assigned 题回 ready，也不把池空降级成 PoW-only。保留全局预算；按站点有界准入、容量保留和告警可用于降低相互影响，但单纯调大预算或调低 TTL 不能代替生命周期修正。

**验收**：分别覆盖 terminal 分批释放、有效 assigned 保留、challenge 到期后的有界释放、图片 TTL 到期兜底、回收与兑换并发、重启、多个站点共享预算及补池恢复。在隔离有界环境模拟只领题后放弃，不要求完成 PoW；明确预算占用、503 出现条件及恢复时限。恢复后旧 challenge 必须仍被拒绝，图片不能重发，其他站点的影响需有实际记录。本轮未做网络容量或 Linux 运行验收。

### F16 · P2 · 服务异常退出与 Shutdown 超时后的资源收尾不完整

`cmd/server/main.go:218` 收到 Serve 错误直接返回；226 行公共 Shutdown 失败也直接返回，后续管理 Shutdown 和 purge 等待不会执行。newHTTPServer 未将请求 ctx 绑定服务生命周期。标准库最小实验确认 Shutdown 超时不等于强制终止在途 handler。

这是代码可见的异常路径缺口；完整服务故障注入本轮未运行。建议使用服务子 context，在所有退出路径取消后台任务、关闭两个 HTTP server、等待 goroutine 后再关库与释放运行锁；超时后明确强制 Close 并报告真实失败。正常停止继续给在途请求合理排空时间。

验收应覆盖一侧 listener 报错、慢请求超过五秒、管理面仍有在途请求、purge 正访问数据库，确保退出有界、不在释放锁后继续写库，也不留下 goroutine 或端口。

## 9. 补充线索复核：未纳入开放缺陷的两项

报告交付后收到两条补充审计线索，已检查当前代码并执行针对性验证。它们不增加第 4、5 节的开放缺陷数量，也不改变上线结论。

### 9.1 nonce 的 int64 回绕在当前输入限制下不可达

补充线索提出 `internal/pow/pow.go:79` 的 `n.Int64()` 可能对大于 MaxInt64 的值回绕，从而绕过 `nonce <= 1e12`。该推断遗漏了 `pow.go:67` 的前置长度校验：只接受最多 16 个字节，随后还限定为 ASCII 十进制数字。

- 所举 `9223372036854775808` 是 **19 位**，在转换前已被拒绝。
- 最大 16 位十进制数 `9999999999999999` 小于 MaxInt64 `9223372036854775807`，因此通过长度和字符检查的数不会发生所述回绕。
- 用**未修改的 pow.go**、Go 1.27.3 在隔离临时目录执行了 9 个边界输入：0、1e12、1e12+1、16 位最大值、MaxInt64、MaxInt64+1、MaxUint64，以及两个前导零边界。全部符合预期；上述超限输入全部被拒绝。

**结论：该“上界可绕过”线索为误报，不作为漏洞或上线阻断项。** 若将来扩大 MaxNonceLen，必须同步复核数值转换并添加对应回归；当前没有因这条线索修改安全代码。

### 9.2 Origin:null 的两种端点策略应明确区分

`internal/api/handlers.go:107` 的公开 challenge/redeem JSON/CORS 路径拒绝 `Origin:null`，与 `docs/DESIGN.md:909` 的来源策略表一致。该行为不是漏实现示例表单的回落逻辑。

回落 `Sec-Fetch-Site` 的实现位于 **示例业务后端** `cmd/exampleapp/main.go:576`，处理原生业务表单提交。其测试 `TestOriginNullFallsBackToSecFetchSite` 本轮用 Go 1.27.3、`-count=1` 定向执行通过：same-origin/same-site 放行，cross-site/cross-origin 拒绝，真实跨站 Origin 即便搭配 same-origin 头仍拒绝。此证据是 Go 端点测试，不是新增浏览器验收。

AGENTS 的阶段摘要与 DESIGN 变更日志没有清楚标注适用端点，容易被误读为所有公开 API 都应放行 null。这属于 F18 的**文档适用范围澄清**：应明确示例业务表单和验证服务 JSON/CORS 的差别，不能把 `Sec-Fetch-Site` 的宽粒度分类当作精确站点 Origin 的替代，也不能为了消除这条误解放宽公开 API 白名单。
